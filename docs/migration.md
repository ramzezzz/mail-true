# Перенос почты в Mail.True (`@mail-true/migrate`)

Модуль переноса почтовых ящиков с чужого сервера на наш по схеме
**IMAP → IMAP**. Главный целевой сценарий — Kerio Connect, но механизм
универсальный и работает с любым IMAP-сервером (Exchange, Zimbra, Dovecot,
Яндекс, Gmail и др.).

Пакет: `packages/migrate/` (`@mail-true/migrate`). Зависимости — только те,
что уже есть в монорепозитории: `imapflow`, `pg`, `zod`, `pino`
(`mailparser` объявлен, но пока не используется — заголовки разбираются
своим лёгким парсером).

## Что сохраняется при переносе

| Что                    | Как                                                        |
|------------------------|------------------------------------------------------------|
| Структура папок        | Вложенность воспроизводится; разделитель иерархии источника (`/`, `.`) заменяется на разделитель приёмника; служебный префикс `INBOX/`/`INBOX.` (Courier, Exchange) отбрасывается автоматически. Имя, которое приёмник не принимает, чинится на лету (см. «Имена папок») |
| Системные флаги        | `\Seen`, `\Answered`, `\Flagged`, `\Draft`, `\Deleted` (не переносится только `\Recent` — им управляет сервер) |
| Пользовательские метки | IMAP-ключевые слова (keywords) переносятся как есть        |
| Дата письма            | `INTERNALDATE` передаётся в `APPEND`                       |
| Содержимое             | Письмо копируется байт в байт (RFC822), включая вложения   |

## Сопоставление папок

Для каждой папки источника решение принимается по порядку:

1. **Переопределение** из настроек (`--map 'Источник=Приёмник'` в CLI или
   `mapping.overrides` в API) — всегда побеждает.
2. **SPECIAL-USE** атрибут, который отдал источник (RFC 6154 / XLIST):
   `\Sent`, `\Drafts`, `\Trash`, `\Junk`, `\Archive`.
3. **Таблица известных имён** спец-папок (см. `src/folder-map.ts`):
   Kerio/Exchange «Sent Items», «Deleted Items», «Junk E-mail»; русские
   «Отправленные», «Черновики», «Корзина», «Удалённые», «Спам»,
   «Нежелательная почта»; Gmail «[Gmail]/Sent Mail» и т.д.
4. Иначе папка считается обычной и переносится с сохранением иерархии.

Имена спец-папок **приёмника** определяются по его собственному
LIST SPECIAL-USE (наш Dovecot отдаёт `Sent`, `Drafts`, `Spam`, `Trash`),
запасной вариант — `DEFAULT_ROLE_TARGETS`. Контейнер `[Gmail]` и
невыбираемые (`\Noselect`) папки пропускаются, их дети переносятся.

## Имена папок

Разделителя иерархии мало. Наш Dovecot отдаёт по IMAP разделитель `/`, но
хранит почту в Maildir++, где уровни разделяются **точкой**. Поэтому папку
вида «Отчёт 2024.финал», «Проект v2.0» или «ООО Ромашка. Договоры» — у Kerio
такие имена обычны — сервер отвергает целиком: `Character not allowed in
mailbox name: '.'`.

Как это решается:

- при создании папки-приёмника отказ по имени не считается сбоем: имя
  чинится (недопустимые символы заменяются на `_`) и папка создаётся под
  безопасным именем. В отчёт и в поток событий уходит `folder-renamed`
  с исходным именем, фактическим и причиной отказа;
- если имя нужно привести заранее и предсказуемо — есть настройка
  `mapping.destUnsafeChars` (в API) и функции `sanitizeDestPath` /
  `MAILDIR_UNSAFE_CHARS`;
- отказ сервера по существу (недопустимое имя, слишком длинное имя) больше
  не повторяется пять раз с нарастающей паузой: это `PermanentFolderError`,
  ответ приходит сразу;
- если папка всё-таки не перенеслась, в счётчик ошибок идёт **число
  непереехавших писем**, а не единица, и в тексте ошибки названы папка,
  количество и причина. Раньше «ошибок: 1» могло означать пять тысяч писем.

## Докачка и защита от дублей

Ключ дедупликации письма:

- нормализованный `Message-ID` (без угловых скобок и пробелов);
- если его нет — `sha256(Date + From + To + Subject + размер)`.

Ключ отвечает на вопрос «похоже ли», а не «то же ли самое»: Message-ID
генерирует отправитель, и он не обязан быть уникальным, а типовые
автоуведомления совпадают по всем заголовкам и размеру. Поэтому решение
принимается **по количеству копий**: пропускается ровно столько писем
источника, сколько копий с таким ключом реально лежит в папке-приёмнике,
всё сверх того считается новым и переносится. Иначе этапный перенос
(полный проход, затем дельта в день переключения MX) терял бы законно
новые письма.

Дедупликация действует в пределах папки-приёмника. Защита двухуровневая:

1. **Содержимое приёмника**: перед переносом каждая папка-приёмник
   сканируется (только заголовки), её письма пересчитываются по ключам.
   Поэтому дубли не появятся, даже если состояние потеряно.
2. **Хранилище состояния** (опция `--state`): сколько копий каждого ключа
   уже перенесено, и курсор по папке источника (`UIDVALIDITY` + последний
   UID) — повторный запуск читает метаданные только новых писем. При таком
   инкрементальном чтении копии, уже занятые прошлыми проходами, из счёта
   вычитаются: иначе новое письмо с повторным `Message-ID` объявлялось бы
   дублём давно перенесённого.

Хранилища: файл JSONL (append-only, переживает обрыв на полуслове) или
Postgres (`pg:postgresql://...` — таблицы `migrate_messages`,
`migrate_cursors` создаются автоматически; в `migrate_messages` есть
столбец `copies`, он создаётся и на уже существующей таблице).

### Курсор и неудавшиеся письма

Курсор папки — это «до какого UID включительно всё разобрано». Он двигается
**только по непрерывному префиксу успешных писем**: первая же неудача его
замораживает. Это принципиально: пока курсор двигался безусловно, сценарий
«квота кончилась посреди переноса» терял почту навсегда — первый проход
давал «скопировано 4, ошибок 6», курсор уезжал в конец, а повторный запуск
с тем же состоянием докачивал ноль и рапортовал «ok, ошибок 0».

Отказ по квоте теперь и называется квотой: в отчёте вместо
`UID 5: Command failed` — «у ящика-приёмника кончилась квота; код сервера
OVERQUOTA; ответ сервера: …», плюс отдельная подсказка на папку о том, что
после подъёма квоты нужно повторить перенос с тем же файлом состояния.

## Устойчивость

- До 5 попыток на папку (настраивается), экспоненциальная пауза,
  переподключение обоих концов.
- В памяти держится максимум одно письмо; метаданные писем — лёгкие
  (UID, размер, флаги, ключ).
- Ошибка отдельного письма не валит перенос: фиксируется в отчёте
  (`status: 'partial'`), остальное продолжает копироваться.
- `--batch-size` — частота записи курсора (по умолчанию каждые 50 писем).
- `maxMessageSize` — сверхбольшие письма можно пропускать с пометкой.

## CLI

```bash
node packages/migrate/dist/cli.js <команда> [параметры]
```

### Перенос одного ящика

```bash
printf '%s' 'пароль-в-kerio' > /root/kerio.pass && chmod 600 /root/kerio.pass
export MIGRATE_DEST_PASS='пароль-у-нас'

node packages/migrate/dist/cli.js run \
  --source-host kerio.example.com --source-port 993 --source-secure \
  --source-user ivanov --source-pass-file /root/kerio.pass \
  --dest-host 127.0.0.1 --dest-port 143 \
  --dest-user ivanov@mail.local \
  --state ./migrate-state/ivanov.jsonl \
  --map 'Public Folders/Общая=Общие/Архив' \
  --exclude 'Календарь' \
  --report ivanov-report.json
```

### Пароли

Аргумент командной строки виден в системе **каждому**: `ps aux` и
`/proc/<pid>/cmdline` читает любой непривилегированный пользователь, а
перенос большого ящика идёт часами. Поэтому пароль берётся из первого
доступного источника в таком порядке:

| Способ | Как |
|---|---|
| файл (лучший) | `--source-pass-file ФАЙЛ` / `--dest-pass-file ФАЙЛ` — читается первая строка |
| названная переменная | `--source-pass-env ИМЯ` / `--dest-pass-env ИМЯ` |
| переменная по умолчанию | `MIGRATE_SOURCE_PASS` / `MIGRATE_DEST_PASS` |
| аргумент (небезопасно) | `--source-pass` / `--dest-pass` — работает, но с предупреждением в stderr |

Полезные флаги: `--dry-run` (показать план сопоставления и объёмы, ничего
не копировать), `--strict-tls` (по умолчанию проверка сертификатов
отключена — у Kerio и в dev сертификаты самоподписанные),
`--batch-size N`, `--max-attempts N`.

### Пакетный перенос

```bash
node packages/migrate/dist/cli.js batch \
  --file accounts.csv --concurrency 2 \
  --dest-host 127.0.0.1 --dest-port 143 \
  --state-dir ./migrate-state --report batch-report.json
```

Формат CSV (заголовок обязателен; разделитель `,` или `;` определяется
автоматически; колонки `dest_host`/`dest_port`/`dest_secure` можно
опустить и задать флагами):

```csv
source_host,source_port,source_secure,source_user,source_pass,dest_user,dest_pass
kerio.old.local,993,true,ivanov,pass1,ivanov@mail.local,newpass1
kerio.old.local,993,true,petrov,pass2,petrov@mail.local,newpass2
```

JSON-формат — массив таких же плоских объектов либо вложенных
`{ "source": {...}, "dest": {...}, "mapping": {...} }`.

Очередь обрабатывается с ограничением параллельности, по каждому ящику —
отдельный отчёт (`ok` / `partial` / `failed`).

### Пользователи Kerio Connect

Kerio Connect (Accounts → Users → выбрать домен → Export) выгружает
CSV-файл `users_<ИмяДомена>_<дата>.csv` с колонками `Name`, `Password`,
`FullName`, `Description`, `MailAddress`, `Groups` (порядок произвольный,
обязательна только `Name`). Встречаются два варианта разделителей, разбор
поддерживает оба (определение — по строке заголовка):

```csv
Name;Password;FullName;Description;MailAddress;Groups
abird;VbD66op1;Alexandra Bird;Development;abird;read,all
```

```csv
Name,Password,FullName,Description,MailAddress,Groups
abird,VbD66op1,Alexandra Bird,Development,abird,"read,all"
```

```bash
node packages/migrate/dist/cli.js kerio-users \
  --file users_example.com_2026-08-05.csv --domain mail.local --out users.json
```

Если `--domain` не задан, домен берётся из имени файла выгрузки.
На выходе — список для создания ящиков у нас: `email`, `displayName`,
`aliases` (второй и последующие адреса из `MailAddress`; `MailAddress`
без домена, как `abird`, дополняется доменом). Дальше ящики создаются
через `infra/scripts/create-mailbox.sh` или напрямую INSERT в
`virtual_users` / `virtual_aliases`.

**Пароли**: Kerio выгружает их **открытым текстом**. По умолчанию CLI
пароли в вывод не включает; флаг `--with-passwords` добавляет их в список —
только для немедленного создания ящиков (пароль сразу перехешировать в
формат Dovecot через `doveadm pw`/`crypt`, сам файл со списком после
использования удалить, в журналы пароли не писать). Файл `--out` создаётся
и пересоздаётся с правами `600`: раньше при обычном umask 022 он получался
`644`, и пароли всех сотрудников читал любой пользователь системы.

**Битая выгрузка**: непарная кавычка больше не съедает остаток файла молча.
Разбор прерывается ошибкой с номером строки, где кавычка открылась, и код
возврата 2. Раньше файл на трёх пользователей с незакрытой кавычкой у
первого разбирался в одного пользователя, весь хвост попадал в его имя, а
ящики для всех последующих просто не создавались — и это замечали по
отбивающейся почте.

Поддерживается и best-effort разбор `users.cfg` (XML из каталога данных
Kerio) — на случай, когда консоль недоступна, а файлы сервера есть.

## Программный интерфейс (для API/админки)

```ts
import { migrateMailbox, MailboxMigrator, createStateStore } from '@mail-true/migrate';

const report = await migrateMailbox({
  source: { host: 'kerio.example.com', port: 993, secure: true, user: 'ivanov', pass: '...', allowInsecureTls: true },
  dest:   { host: '127.0.0.1', port: 143, user: 'ivanov@mail.local', pass: '...', allowInsecureTls: true },
  state: createStateStore('pg:postgresql://mailserver:...@127.0.0.1:5432/mailserver'),
  onProgress: (e) => { /* события для веб-сокета админки */ },
});
```

События прогресса (`ProgressEvent`): `folders` (план сопоставления),
`start`, `folder-start`, `message` (copied/skipped/failed + счётчики),
`folder-done`, `retry` (с указанием папки), `folder-renamed` (имя папки не
принято приёмником), `done` (итоговый `MailboxReport`). Тот же поток
событий доступен через `new MailboxMigrator(opts).on('progress', ...)`.
Пакетный режим — `migrateBatch()` / `parseAccountsList()`.

## Известные ограничения

- Переносится только почта: календари/контакты/задачи Kerio по IMAP
  недоступны.
- Флаг `\Recent` и порядок UID у приёмника не сохраняются (это нормально
  для IMAP-переноса; клиенты ориентируются на даты и флаги).
- Если одно и то же письмо лежит в двух папках источника, которые
  отображаются в одну папку приёмника, копий будет столько же, сколько в
  источнике: дедупликация считает копии, а не факт наличия ключа.
- `users.cfg` разбирается упрощённым XML-парсером (полноценного XML-парсера
  в зависимостях нет) — основной путь остаётся CSV-экспорт.
