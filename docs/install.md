# Установка Mail.True на боевой сервер

Инструкция для Ubuntu Server 22.04. Всё, что нужно, — сервер, домен и
пятнадцать минут. Установщик лежит в `install/`, ставится одной командой.

## 1. Что нужно от сервера

| Требование           | Минимум             | Комфортно      | Почему                                                                                   |
| -------------------- | ------------------- | -------------- | ---------------------------------------------------------------------------------------- |
| ОС                   | Ubuntu Server 22.04 | она же         | на ней всё проверялось; 20.04, 24.04 и Debian 11/12 тоже работают                        |
| Память               | 2 ГБ                | 4 ГБ           | весь продукт в простое занимает **370–400 МБ**; остальное — письма, поиск, пики нагрузки |
| Память с антивирусом | 3 ГБ                | 4 ГБ           | ClamAV с базами добавляет около 1 ГБ                                                     |
| Диск                 | 10 ГБ               | 20 ГБ и больше | образы около 1.9 ГБ, дальше — сами письма                                                |
| Процессор            | 1 ядро              | 2 ядра         | x86_64 или aarch64                                                                       |
| Права                | root                |                | нужен для Docker, портов ниже 1024 и сертификатов                                        |

Ещё нужны две вещи, которые нельзя получить командой на сервере:

**Домен**, у которого вы можете править DNS-записи. Без этого почта не будет
ни приходить, ни приниматься чужими серверами.

**Открытый исходящий порт 25.** Многие хостеры закрывают его по умолчанию,
чтобы с их адресов не рассылали спам. Симптом потом такой: почта приходит,
а исходящие письма молча копятся в очереди. Установщик проверяет это заранее
и говорит прямо. Открывают обычно после короткой переписки с поддержкой —
достаточно объяснить, что поднимаете свой почтовый сервер.

**Проверить заранее, до установки:**

```bash
# должно подключиться и показать приветствие вида «220 mx.google.com ESMTP»
nc -vz gmail-smtp-in.l.google.com 25
```

### Порты, которые займёт сервер

| Порт      | Кто     | Зачем                                                                     |
| --------- | ------- | ------------------------------------------------------------------------- |
| 25        | Postfix | приём почты от чужих серверов                                             |
| 587       | Postfix | отправка почтовыми клиентами (STARTTLS + пароль)                          |
| 143 / 993 | Dovecot | IMAP и IMAPS                                                              |
| 110 / 995 | Dovecot | POP3 и POP3S                                                              |
| 80        | Nginx   | почта и админка в браузере, автонастройка клиентов, продление сертификата |
| 443       | Nginx   | то же по HTTPS — и почта, и Outlook работают только так                   |

| 465 | Postfix | отправка почтовыми клиентами (TLS сразу, без STARTTLS) |

Порт **465** (submissions, «TLS сразу») публикуется наружу наравне с 587.
Служба `submissions` в `infra/postfix/conf/master.cf` защищена так же,
как 587: обязательные TLS, пароль и проверка «отправитель принадлежит
вошедшему».

Раньше этот порт на боевом сервере наружу не выпускался — в
`install/compose.prod.yml` у postfix были перечислены только 25 и 587,
и открыть 465 предлагалось руками. Это был дефект, а не выбор: Postfix
порт слушал, справка «Настроить почтовую программу» его печатала, а
подключиться было нельзя. Причём проявлялось это **только на боевом
сервере** — стенд разработчика (`infra/docker-compose.yml`) 465 публикует
всегда, поэтому при разработке всё выглядело исправным.

Сервис автонастройки (`apps/autoconfig`) выдаёт почтовым программам оба
порта: 587 со STARTTLS первым (основной выбор клиента) и 465 «TLS сразу»
вторым — его по привычке предпочитают Outlook и почта Apple.

Служебные порты (Postgres 5432, Redis 6379, веб-интерфейс Rspamd 11334,
отладочный порт автонастройки 8025) публикуются **только на 127.0.0.1**
и снаружи недоступны — так и задумано. Сервер приложения (порт 3000),
почта и админка на боевом сервере не публикуются вовсе: наружу их отдаёт
только nginx на 80 и 443.

### Второй стенд на той же машине

Держать рядом с рабочим сервером тестовый контур — или проверить
обновление, не трогая боевой, — можно. Имена контейнеров складываются из
имени проекта Docker Compose (`<проект>-<сервис>-<номер>`), и достаточно
дать второму стенду своё. Раньше это было невозможно вовсе: имена были
зашиты (`container_name: mail-postgres`), а такое имя глобально на весь
демон Docker — второй `docker compose up` падал на первом же сервисе
с «Conflict. The container name "/mail-postgres" is already in use».

Во втором `infra/.env` обязаны отличаться три группы значений:

```ini
COMPOSE_PROJECT_NAME=mailtrue2          # имена контейнеров, томов и сети
DOCKER_SUBNET=172.29.0.0/16             # подсеть стека
RESOLVER_IP=172.29.0.53                 # фиксированные адреса внутри неё
DOVECOT_IP=172.29.0.54
SMTP_PORT=2525                          # и все публикуемые порты
SUBMISSION_PORT=2587
...
```

Порты сдвигать нужно потому, что занять 25-й дважды нельзя ничем: второй
стенд поднимается без боевого переопределения портов
(`MT_USE_PROD_OVERRIDE=0`), с публикацией на 127.0.0.1 из `infra/.env`.
Обращаться к контейнерам второго стенда — через compose из его каталога
(`docker compose -f infra/docker-compose.yml exec postgres …`), а не по
имени контейнера.

## 2. Установка

### Одной командой

```bash
sudo apt-get update && sudo apt-get install -y git
git clone <адрес репозитория> /opt/mailtrue
cd /opt/mailtrue
sudo bash install/install.sh
```

Установщик спросит четыре вещи: домен, имя сервера, адрес и пароль
администратора, нужен ли антивирус. Всё остальное — пароли базы, Redis,
ключи шифрования — он придумает сам, случайными.

Что происходит по шагам:

1. **Проверка системы.** Версия ОС, память, диск, свободны ли порты, не стоит
   ли уже чужой почтовый сервер, открыт ли исходящий 25-й. Найденный чужой
   Postfix или exim установщик **отключает сам** (`systemctl disable --now`) —
   иначе он держит 25-й порт и наш Postfix не запустится. Пакет при этом
   остаётся в системе: удалять чужое установщик не берётся, только говорит.
2. **Docker.** Ставится с официального репозитория, если его ещё нет.
   Docker, поставленный **из snap**, установщик заменяет на официальный.
   Причина не в предпочтениях: snap-пакету видны только домашние каталоги,
   `/opt` для него не существует. Внешне это выглядит как пропажа файлов —
   `ls` показывает `infra/docker-compose.yml`, а docker на тот же путь
   отвечает `no such file or directory`. Стек в таком Docker не поднимется
   в принципе: конфигурация Postfix, Dovecot и Rspamd монтируется в
   контейнеры из каталога проекта. Если в snap-Docker есть посторонние
   контейнеры, установщик спросит перед заменой.
3. **Вопросы.**
4. **Секреты и конфигурация** — пишутся в `infra/.env` с правами 600.
5. **Временный самоподписанный сертификат** — чтобы стек вообще поднялся.
6. **Сборка и запуск стека.** Первый раз это 3–7 минут: собираются образы
   Postfix, Dovecot, Rspamd, сервиса автонастройки, сервера приложения
   и обоих веб-интерфейсов — почты и админки.
7. **Ящик и учётная запись администратора**, алиасы `postmaster@` и `abuse@`.
8. **Настоящий сертификат Let's Encrypt**, если домен уже указывает на сервер.
9. **DNS-записи** — печатаются в готовом для копирования виде.
10. **Адреса, по которым всё открывается** — почта и админка.

Замеры на нашем стенде (контейнер с чистой Ubuntu 22.04, быстрый канал):

| Что                                                                 | Время         |
| ------------------------------------------------------------------- | ------------- |
| Установка с нуля: скачать и собрать образы, поднять стек, настроить | около 2 минут |
| Повторный запуск установщика (ничего не изменилось)                 | 8 секунд      |
| Переустановка после снятия (образы уже собраны)                     | 34 секунды    |

К этому добавьте установку самого Docker — около минуты. Сборка образов
веб-интерфейса добавляет к первой установке ещё 1–2 минуты.

### Где всё открывается

Установщик печатает это в конце, но чтобы знать заранее:

| Адрес                                      | Что там                                            |
| ------------------------------------------ | -------------------------------------------------- |
| `https://mail.<домен>` и `https://<домен>` | почта. Логин — полный адрес ящика, пароль — его же |
| `https://admin.<домен>`                    | админка: домены, ящики, алиасы, DNS, журнал аудита |
| `https://autoconfig.<домен>`               | страница помощи по ручной настройке клиента        |

Почта и админка появятся, как только разойдутся DNS-записи `mail.<домен>` и
`admin.<домен>` (см. раздел 3). До этого момента стек уже работает — просто
браузеру некуда прийти.

### Без вопросов (повторные установки, автоматизация)

```bash
cp install/answers.example.env /root/mailtrue.env
nano /root/mailtrue.env          # домен, хост, администратор, пароль
chmod 600 /root/mailtrue.env
sudo bash install/install.sh --answers /root/mailtrue.env
```

То же самое через переменные окружения:

```bash
sudo MAILTRUE_DOMAIN=example.ru \
     MAILTRUE_HOSTNAME=mail.example.ru \
     MAILTRUE_ADMIN_EMAIL=admin@example.ru \
     MAILTRUE_ADMIN_PASSWORD='длинный-пароль' \
     bash install/install.sh --non-interactive
```

Если пароль администратора не задан, установщик придумает случайный
и покажет его в конце — не потеряйте вывод.

Что установщик теперь **отвергает**, а не проглатывает молча:

- пароль-заглушку из примера (`смените-этот-пароль`, `change-me…` и подобные).
  Заглушка длиннее десяти символов и проверку длины проходила — боевые
  серверы уезжали в работу с паролем, который лежит в репозитории.
  `install/selfcheck.sh` дополнительно сверяет хэш пароля администратора
  в базе с этим списком и проверяет ящик через `doveadm auth test`;
- опечатку в `MAILTRUE_TLS` (допустимо `letsencrypt` или `selfsigned`) и
  в `MAILTRUE_CLAMAV` (`yes`/`no` в любом регистре, плюс `да`/`нет`).
  Раньше `letsencript` молча означало `letsencrypt`, а `yse` — `no`;
- занятые чужими процессами порты: раньше было только предупреждение,
  и установка шла дальше до падения `docker compose up` с сырой ошибкой.
  Теперь спрашивается подтверждение (в неинтерактивном режиме — отказ,
  если явно не задан `--yes`).

Полезные ключи:

| Ключ                    | Что делает                                                   |
| ----------------------- | ------------------------------------------------------------ |
| `--prepare-only`        | только проверки, секреты и конфигурация; стек не поднимается |
| `--skip-port-check`     | не проверять порты (для стендов внутри контейнеров)          |
| `--skip-docker-install` | не трогать Docker                                            |
| `--yes`                 | соглашаться на все подтверждения                             |

### Повторный запуск ничего не сломает

Установщик идемпотентен, и это проверено: второй запуск оставляет
`infra/.env` побайтово тем же, не меняет пароль существующего администратора,
не плодит ящики и алиасы, не трогает письма. Поэтому его можно спокойно
запускать ещё раз — например, чтобы включить антивирус или перевыпустить
сертификат после того, как DNS наконец разошёлся.

## 3. DNS: какие записи и зачем

Полный список с настоящим ключом DKIM установщик печатает в конце и
сохраняет в `install/state/dns-records.txt`. Получить его в любой момент:

```bash
curl "http://127.0.0.1:8025/api/dns-records?domain=example.ru"
```

Ниже — что каждая запись значит. Замените `example.ru` на свой домен,
`mail.example.ru` — на имя сервера, `203.0.113.10` — на его адрес.

### Обязательный минимум

**A — где стоит сервер**

```
mail.example.ru.    A    203.0.113.10
```

Всё остальное ссылается на это имя. Без A-записи не выпустится сертификат
и чужие серверы не найдут, куда доставлять почту.

**MX — куда доставлять почту домена**

```
example.ru.    MX    10 mail.example.ru.
```

Чужой сервер, отправляя письмо на `кто-то@example.ru`, спрашивает у DNS
MX-запись и идёт на указанный хост. Число 10 — приоритет; при одном сервере
оно ни на что не влияет. Точка в конце обязательна: без неё многие панели
дописывают домен ещё раз и получается `mail.example.ru.example.ru`.

**SPF — кому разрешено отправлять от имени домена**

```
example.ru.    TXT    "v=spf1 mx ~all"
```

`mx` означает «отправлять могут те хосты, что указаны в MX» — то есть наш
сервер. `~all` — «остальные подозрительны» (мягкий отказ). Без SPF письма
почти гарантированно попадают в спам.

**DKIM — подпись исходящих писем**

```
mail._domainkey.example.ru.    TXT    "v=DKIM1; k=rsa; p=MIIBIjANBg..."
```

Ключ генерирует Rspamd при первом запуске; публичную часть берите из
`install/state/dns-records.txt` — она длинная, и её нельзя сокращать.
Получатель проверяет подпись этим ключом и убеждается, что письмо не
подменили по дороге. Многие панели DNS требуют разбить длинное значение
на куски по 255 символов — это нормально, склеивается автоматически.

**DMARC — что делать с письмами, не прошедшими проверку**

```
_dmarc.example.ru.    TXT    "v=DMARC1; p=quarantine; rua=mailto:postmaster@example.ru; adkim=s; aspf=s"
```

`p=quarantine` — «подозрительные класть в спам». `rua` — адрес, куда
почтовые службы будут слать отчёты. Начинать лучше с `p=none` (только
отчёты, ничего не блокировать) и переходить к `quarantine`, когда убедитесь,
что своя почта проходит проверки.

**PTR — обратная запись**

```
203.0.113.10    PTR    mail.example.ru.
```

Это единственная запись, которую **нельзя** сделать у регистратора домена:
обратной зоной владеет тот, кому принадлежит IP-адрес. Настраивается в
панели хостинга (раздел обычно называется rDNS или «обратная зона»), иногда
только через поддержку.

Без PTR или при несовпадении имени Google, Mail.ru и Яндекс отклоняют
письма ещё на этапе подключения. Имя в PTR должно совпадать с тем, чем
сервер представляется (`MAIL_HOSTNAME`), а это имя должно резолвиться
обратно в тот же адрес.

### Для веб-интерфейса

```
example.ru.          A        203.0.113.10
mail.example.ru.     CNAME    mail.example.ru.
admin.example.ru.    CNAME    mail.example.ru.
```

Почта открывается и на самом домене (`https://example.ru`), и на
`https://mail.example.ru`; админка — только на `https://admin.example.ru`.

Отдельное имя у админки — не украшение. Во-первых, браузер держит cookie
почты и cookie админки раздельно, и одна не может случайно стать другой.
Во-вторых, админку удобно закрыть целиком — по адресу или за VPN, — не
трогая вход в почту. Если админка снаружи не нужна вовсе, просто не
публикуйте запись `admin.` — почта от этого не пострадает.

### Для автонастройки почтовых клиентов

```
autoconfig.example.ru.       CNAME    mail.example.ru.
autodiscover.example.ru.     CNAME    mail.example.ru.
_imaps._tcp.example.ru.      SRV      0 1 993 mail.example.ru.
_submission._tcp.example.ru. SRV      0 1 587 mail.example.ru.
_pop3s._tcp.example.ru.      SRV      0 1 995 mail.example.ru.
_autodiscover._tcp.example.ru. SRV    0 0 443 mail.example.ru.
```

Благодаря им пользователь вводит в Thunderbird или Outlook только адрес и
пароль, а клиент сам находит серверы и порты. Подробности — `docs/autoconfig.md`.

### Проверить, что записи разошлись

```bash
sudo bash install/selfcheck.sh          # проверит все записи разом
dig +short MX example.ru                # или по одной
dig +short TXT mail._domainkey.example.ru
dig +short -x 203.0.113.10              # PTR
```

DNS расходится не мгновенно: обычно минуты, иногда до суток (зависит от TTL
прежних записей). Если `selfcheck.sh` показывает «не опубликована» сразу
после правки — просто подождите и повторите.

## 4. Проверка после установки

```bash
sudo bash install/selfcheck.sh
```

Скрипт проходит по всем пунктам и по каждому непройденному объясняет, что
именно сделать. Что он проверяет:

1. **Сервисы** — все контейнеры запущены и здоровы, сколько занимают памяти.
2. **Свой резольвер** — отвечает ли контрольная запись Spamhaus. Это самая
   тихая из возможных поломок: без своего резольвера бесплатные списки спама
   молча перестают отвечать, и фильтр выглядит работающим, ничего не ловя.
3. **Порты** — слушаются ли и слушаются ли снаружи, а не только на localhost;
   открыт ли исходящий 25-й.
4. **DNS** — каждая запись резолвится вживую и сравнивается с ожидаемой,
   отдельно проверяется PTR.
5. **Сертификат** — настоящий или самоподписанный, какие имена покрывает,
   сколько дней до истечения, отдают ли его на самом деле порты 993, 443 и 587.
6. **DKIM** — есть ли ключ у Rspamd и совпадает ли он с опубликованным в DNS.
   Несовпадение хуже отсутствия: подпись есть, а проверить её нельзя.
7. **Почта в обе стороны** — реальное письмо снаружи доходит до ящика, письмо
   изнутри отправляется через 587 и подписывается DKIM.
8. **Веб-интерфейс** — почта и админка отдаются через nginx, сервер
   приложения отвечает на `/api`.
9. **Безопасность и место** — права на `infra/.env`, пароли не из примера
   (включая сверку хэша пароля администратора и пароля его ящика с
   заглушками из `answers.example.env`), принимается ли пароль без
   шифрования, концы строк в `infra/.env`, когда последний раз делали
   резервную копию. Место на диске проверяется **дважды**: там, где лежит
   репозиторий, и там, где docker держит тома (обычно `/var/lib/docker`).
   На сервере это сплошь и рядом разные разделы, и кончается первым тот,
   что с письмами, — а проверка раньше смотрела только на первый и бодро
   докладывала «свободно 200 ГБ», пока почта уже переставала приниматься.
10. **Схема базы соответствует версии продукта** — все таблицы и колонки из
    `infra/postgres/migrations/` есть в базе. Непринятая миграция не ломает
    ничего громко: стек поднимается, почта идёт, молча отваливается только
    новое — отложенная отправка, отложенные письма, контакты, показатели.
    Здесь же проверяются служебный вход Dovecot (без него администратор не
    откроет чужой ящик, а сборщик внешней почты не заработает) и посредник
    к очереди Postfix (без него раздел «Очередь» в панели недоступен).

Отдельно от `selfcheck.sh` есть быстрые юнит-тесты самих скриптов —
им не нужны ни Docker, ни поднятый стек:

```bash
bash install/selftest.sh
```

Они проверяют разбор ответов (опечатка не должна становиться значением по
умолчанию), распознавание паролей-заглушек, полноту списка томов для
резервной копии и развязку `infra/.env` с томом базы при восстановлении,
а ещё — согласованность `infra/.env.example`, `docker-compose.yml` и
установщика: что каждый ключ примера куда-то подставляется, что пустые
ключи установщик заполняет, что сборка образов не зависит от файлов,
скрытых от репозитория, и что нигде не завелись концы строк Windows.

Полезные ключи:

```bash
sudo bash install/selfcheck.sh --quick                 # без проверки доставки
sudo bash install/selfcheck.sh --external you@ya.ru    # ещё и письмо наружу
```

Код возврата 0 — всё хорошо или есть только предупреждения, 1 — есть
проваленные пункты.

## 5. Если письма уходят в спам

Почти всегда причина в одном из шести пунктов, по убыванию частоты:

**1. Нет PTR или он не совпадает.** Проверьте `dig +short -x <IP>`. Должно
вернуть ровно то имя, которым представляется сервер. Настраивается в панели
хостинга, не у регистратора домена.

**2. Не опубликован или не совпадает DKIM.** `sudo bash install/selfcheck.sh`
сравнивает опубликованный ключ с настоящим. Если сервер переустанавливали
с нуля, ключ сменился, а в DNS остался старый — подпись перестала проверяться.

**3. Нет SPF или он слишком широкий.** `v=spf1 mx ~all` — рабочий вариант.
Если письма уходят ещё и через сторонний сервис рассылок, его нужно добавить
в SPF, иначе его письма будут отклоняться.

**4. Адрес сервера в чёрных списках.** Это частая история для новых VPS: адрес
достался «в наследство» от спамера. Проверить:

```bash
# Spamhaus: адрес 203.0.113.10 → перевёрнутый 10.113.0.203
docker compose -f infra/docker-compose.yml exec unbound \
  dig @127.0.0.1 +short 10.113.0.203.zen.spamhaus.org
```

Пустой ответ — адреса в списке нет. Если ответ вида `127.0.0.x` — есть,
и надо запросить исключение на сайте списка (обычно делается за день) или
просить у хостера другой адрес.

**5. Домен слишком новый.** Крупные почтовые службы не доверяют доменам,
которые никогда раньше не слали почту. Лечится только временем и постепенным
наращиванием объёма: несколько писем в день первую неделю, не рассылка сразу
на тысячу адресов.

**6. Содержимое письма.** Одна картинка без текста, куча ссылок на сокращатели,
письмо только в HTML без текстовой части — всё это добавляет очков спама.
Посмотреть, что именно насчитал Rspamd своему же исходящему письму, можно
в его веб-интерфейсе:

```bash
ssh -L 11334:127.0.0.1:11334 root@mail.example.ru   # пробросить порт к себе
# затем открыть http://127.0.0.1:11334, пароль — RSPAMD_PASSWORD из infra/.env
```

Отдельно проверьте себя со стороны: отправьте письмо на mail-tester.com или
на свой ящик в Gmail и посмотрите в исходном виде письма строки
`Authentication-Results` — там будет прямо написано `spf=pass`, `dkim=pass`,
`dmarc=pass` или причина отказа.

Подробности про антиспам, списки и пороги — `docs/antispam.md`.

## 6. Обслуживание

### Состояние и журналы

```bash
cd /opt/mailtrue
DC="docker compose -f infra/docker-compose.yml -f install/compose.prod.yml"

$DC ps                                  # что запущено и здорово ли
$DC logs -f postfix                      # журнал приёма и отправки
$DC logs --tail=100 dovecot              # журнал IMAP и доставки
docker stats --no-stream                 # сколько кто ест памяти
$DC exec postfix mailq                   # очередь неотправленных писем
```

### Забыт пароль от панели

Войти, чтобы сменить пароль, в этот момент нельзя по определению, а
восстановления по письму у панели нет и не будет: оно означало бы, что
доступ к панели равен доступу к ящику. Поэтому — с сервера:

```bash
cd /opt/mailtrue
sudo bash install/reset-admin-password.sh --list   # кто заведён
sudo bash install/reset-admin-password.sh admin    # спросит новый пароль дважды, не показывая
```

Скрипт считает тот же хеш, что и панель (одной и той же программой —
разойтись с ней невозможно), обнуляет счётчик неудачных попыток и
снимает блокировку: иначе после десятка попыток вспомнить пароль вход не
пустил бы ещё пятнадцать минут уже с новым паролем.

### Веб-интерфейс

```bash
$DC logs --tail=100 api                  # журнал сервера приложения
$DC restart api                          # перезапустить сервер приложения
$DC build web admin && $DC up -d web admin   # пересобрать интерфейс и админку
$DC restart nginx                        # после правки infra/nginx/templates/
```

Проверить, что интерфейс жив, не открывая браузер:

```bash
# почта отдаётся                                        -> 200
curl -s -o /dev/null -w '%{http_code}\n' https://mail.example.ru/
# сервер приложения отвечает (401 «нет сессии» — это норма и признак жизни)
curl -s -o /dev/null -w '%{http_code}\n' https://mail.example.ru/api/folders
# админка отдаётся                                      -> 200
curl -s -o /dev/null -w '%{http_code}\n' https://admin.example.ru/
```

### Ящики и пользователи

```bash
bash infra/scripts/create-mailbox.sh user@example.ru 'пароль'   # создать/сменить пароль
$DC exec dovecot doveadm quota get -u user@example.ru           # занятое место
$DC exec postgres psql -U mailserver mailserver -c \
   'SELECT email, active, quota_bytes FROM virtual_users ORDER BY email;'
```

### Сертификат

```bash
sudo bash install/renew-certs.sh            # продлить, если пора
sudo bash install/renew-certs.sh --force    # выпустить заново прямо сейчас
```

Установщик включает systemd-таймер `mailtrue-certs.timer`, который проверяет
срок дважды в сутки. Проверить, что он жив:

```bash
systemctl list-timers mailtrue-certs.timer
```

На время выпуска сертификата nginx останавливается примерно на минуту
(certbot слушает 80-й порт сам). Почта в это время ходит без перерыва —
останавливается только веб-вход автонастройки.

### Антивирус: включить или выключить потом

```bash
# включить
sed -i 's/^CLAMAV_ENABLED=.*/CLAMAV_ENABLED=true/' infra/.env
$DC --profile clamav up -d
# первые 5–10 минут ClamAV качает базы, и всё это время он «нездоров» —
# почта при этом продолжает ходить (при недоступном антивирусе письма
# пропускаются дальше, а не задерживаются)

# выключить
sed -i 's/^CLAMAV_ENABLED=.*/CLAMAV_ENABLED=false/' infra/.env
$DC --profile clamav rm -sf clamav
```

### Безопасность: одна настройка, которую стоит поменять руками

В `infra/dovecot/conf/dovecot.conf.template` стоит `disable_plaintext_auth = no` —
это удобно при разработке, но означает, что Dovecot примет пароль без
шифрования. На боевом сервере поставьте `yes` и перезапустите:

```bash
sed -i 's/^disable_plaintext_auth = no/disable_plaintext_auth = yes/' \
    infra/dovecot/conf/dovecot.conf.template
$DC restart dovecot
```

`selfcheck.sh` показывает эту настройку отдельным пунктом.

## 7. Резервные копии и восстановление

### Копия

```bash
sudo bash install/backup.sh                     # в /var/backups/mailtrue
sudo bash install/backup.sh --dir /mnt/backup   # в другое место
sudo bash install/backup.sh --keep 14           # хранить 14 последних
```

В копию попадают: база целиком (домены, ящики, алиасы, администраторы,
настройки, журналы), Maildir со всеми письмами, **очередь Postfix**
(том `postfix-spool` — принятые, но ещё не доставленные письма),
**обучение антиспама** (том `redisdata` — байесовская статистика),
незавершённые загрузки вложений, ключи DKIM, `infra/.env`, TLS-сертификаты и
списки антиспама. Внутри архива лежит опись `manifest.txt` и контрольные
суммы всех файлов.

**Про обучение антиспама.** Оно живёт в Redis, а не рядом с остальными
данными антиспама, и до недавнего времени в копию не попадало: том Redis
числился «просто кэшем». Восстановление из такой копии молча обнуляло
обучение — каждую пометку «это спам», сделанную людьми за месяцы. Ничто при
этом не ломалось: сервер просто снова начинал ошибаться в раскладке, и понять
почему было уже невозможно. Перед снятием копии `backup.sh` просит Redis
сбросить данные на диск, иначе в архив попал бы файл часовой давности.

Список томов, попадающих в копию, задан ОДИН раз в `install/lib/common.sh`
(`MT_BACKUP_VOLUMES`) и используется и `backup.sh`, и `restore.sh`. Раньше
перечни были раздельные, и появившийся в стеке том очереди Postfix в копию
не попал — а потеря очереди означает тихую потерю уже принятых писем.
`install/selftest.sh` следит, чтобы новый том из `docker-compose.yml` нельзя
было забыть: неизвестный том, не отмеченный как заведомо ненужный, роняет
проверку.

Что намеренно НЕ сохраняется, и почему это решение, а не забывчивость:

| Том         | Почему не в копии                                                                       |
| ----------- | --------------------------------------------------------------------------------------- |
| `pgdata`    | вместо него логический дамп `pg_dump` — он переносим между версиями Postgres, а том нет |
| `mailindex` | индексы Dovecot и поиска выводятся из самих писем, а места занимают столько же          |
| `clamav-db` | базы антивируса скачиваются заново за несколько минут                                   |

После восстановления Dovecot соберёт свои индексы сам при первом обращении к
папке, а полнотекстовый поиск заработает не сразу — запустите
`bash infra/scripts/fts-reindex.sh`.

**Ключи DKIM в копии — важная часть.** Если восстановить почту без них,
подпись сменится, и придётся менять TXT-запись в DNS.

Раз в сутки по расписанию:

```bash
sudo crontab -e
# 30 3 * * * /bin/bash /opt/mailtrue/install/backup.sh --keep 14 >> /var/log/mailtrue-backup.log 2>&1
```

Копии стоит увозить с сервера — диск умирает вместе с копиями на нём:

```bash
rsync -az /var/backups/mailtrue/ backup@другой-сервер:/backups/mail/
```

### Восстановление

```bash
sudo bash install/restore.sh /var/backups/mailtrue/mailtrue-20260805-030000.tar.gz --dry-run
sudo bash install/restore.sh /var/backups/mailtrue/mailtrue-20260805-030000.tar.gz
```

`--dry-run` показывает опись и проверяет контрольные суммы, ничего не меняя.
Обычный запуск спрашивает подтверждение, делает страховочную копию текущей
базы в `install/state/`, замещает базу, письма и ключи, поднимает стек и
печатает, сколько получилось доменов, ящиков и файлов писем — эти числа
надо сверить с описью.

Можно восстановить только часть: `--only db`, `--only mail`, `--only config`.

#### Что происходит с `infra/.env` при восстановлении

`infra/.env` восстанавливать **обязательно**: в нём ключи шифрования
(`AI_ENCRYPTION_KEY`, `EXTERNAL_ACCOUNTS_KEY`, `SESSION_SECRET`), без которых
сохранённые в базе секреты уже не прочитать.

Но пароль Postgres к данным отношения не имеет: он задаётся один раз при
инициализации ПУСТОГО тома базы и потом переменной окружения не меняется.
Поэтому при восстановлении копии в **чистое окружение** (свежая установка,
свой пароль в новом томе) файл из копии разъезжался с томом: сама база
работала — её проверка здоровья ходит локальным сокетом, где пароль не
спрашивают, — а `api`, `postfix` и `dovecot`, которые ходят по TCP, доступ
теряли. Скрипт при этом рапортовал успех.

Теперь `.env` берётся из копии целиком, а ключи, привязанные к тому базы
(`MT_VOLUME_BOUND_ENV_KEYS`: `POSTGRES_USER`, `POSTGRES_PASSWORD`,
`POSTGRES_DB`), возвращаются из действующей установки. Прежние значения
остаются в `infra/.env.before-restore` — они нужны, если вместе с дампом
переносили и сам том `pgdata`.

В конце `restore.sh` проверяет доступ к базе **по паролю и по TCP** (так же,
как это делают сервисы), и завершается с ненулевым кодом, если хоть один
пункт не пройден. Если пароль всё-таки разошёлся, есть два пути:

```bash
# 1) вернуть пароль из копии
grep POSTGRES_PASSWORD infra/.env.before-restore

# 2) или сменить пароль в самой базе
docker compose -f infra/docker-compose.yml exec -T postgres \
  psql -U postgres -c "ALTER USER mailserver PASSWORD 'новый';"
```

#### Копия старее, чем установка

Дамп замещает схему целиком — вместе с ней откатывается и её версия.
Поэтому после загрузки дампа `restore.sh` заново применяет все миграции из
`infra/postgres/migrations/` (они идемпотентны). Без этого восстановление
старой копии на более новую установку оставляло базу без таблиц, появившихся
позже, — ровно как это было при обновлении до появления перебора каталога.

**Копия, из которой ни разу не восстанавливались, копией не является.**
Проверьте её хотя бы раз на другой машине: поставьте туда Mail.True,
восстановите копию и убедитесь, что письма на месте. Именно так проверялись
эти скрипты: копия, изменение (новый ящик и новое письмо), восстановление,
сверка — состояние возвращается ровно к моменту копии.

## 8. Обновление

```bash
cd /opt/mailtrue
sudo bash install/backup.sh            # сначала копия, всегда
git pull
sudo bash install/install.sh --answers /root/mailtrue.env   # или без ключа, интерактивно
```

Установщик пересоберёт изменившиеся образы, применит новые миграции базы
и поднимет стек заново. Пароли и данные не трогаются. Веб-интерфейс при этом
обновляется вместе со всем остальным: файлы сборки лежат внутри образов, и
у каждого в имени хеш содержимого — браузер пользователя подхватит новую
версию сразу, не показывая наполовину старую страницу.

**Порядок при обновлении такой:** сначала поднимается одна база и на неё
ложится новая схема, и только потом собираются образы и запускается новый
код. Это не мелочь. Сборка образов занимает до четверти часа, и раньше всё
это время новый код работал против СТАРОЙ схемы: планировщики отложенной
отправки, отложенных писем, сбора контактов и показателей обращались к
таблицам, которых ещё нет. Сервер от этого не падал, но каждый такой тик
терялся — письмо, которому полагалось уйти по расписанию, в этот тик
не уходило.

**Если миграция не применилась, установщик останавливается** и печатает
причину, которую вернул psql. Продолжать нельзя: неполная схема означает,
что часть разделов панели будет отвечать ошибкой каждому, кто их откроет,
а сообщение об этом потерялось бы среди сотни строк вывода. Отказ
происходит ДО сборки образов, поэтому работающий сервер остаётся на прежнем
коде и прежней схеме — то есть продолжает работать. Разберитесь с причиной
и запустите `install.sh` заново: повторный запуск безопасен.

Проверить, что схема совпала с версией продукта, можно и отдельно —
`sudo bash install/selfcheck.sh` сверяет все таблицы и колонки из каталога
`infra/postgres/migrations/` с тем, что есть в базе.

### Журнал применённых миграций

Что уже накатано на эту базу, записано в таблице `schema_migrations`:
имя файла, номер, контрольная сумма содержимого и время применения.

```bash
$DC exec -T postgres psql -U mailserver -d mailserver \
  -c "SELECT version, name, applied_at, applied_by FROM schema_migrations ORDER BY filename"
```

Установщик применяет только то, чего в журнале нет либо чья контрольная
сумма разошлась с файлом (файл поправили после выпуска). Раньше журнала не
было вовсе: при каждом запуске применялся ВЕСЬ каталог, и содержательные
миграции выполнялись заново — например, та, что восстанавливает направление
у записей истории доставки, каждый раз проходила по всей таблице. А ответить
на вопрос «какие миграции здесь применены» можно было только косвенно,
проверяя, появилась ли нужная таблица.

**На сервере, который стоит давно, журнал появится пустым** — записывать
его было некуда. Поэтому первый запуск после обновления ведёт себя как
раньше: применяет каталог целиком (все файлы идемпотентны) и заполняет
журнал. Со второго запуска применяется только новое. Отметить весь каталог
применённым «задним числом» было бы неверно: сервер может стоять на версии
0015, а в каталоге лежать 0021 — и такая отметка тихо пропустила бы шесть
настоящих миграций.

Индексы на таблицах, в которые идёт постоянная запись, строятся с
`CONCURRENTLY`: обычный `CREATE INDEX` держал бы запись в таблице до конца
построения, а обновление запускают на работающем сервере.

Обновить только базовые образы (Postgres, Redis, Nginx) до свежих версий:

```bash
$DC pull && $DC up -d
```

## 9. Снятие сервера

```bash
sudo bash install/uninstall.sh            # остановить, данные оставить
sudo bash install/uninstall.sh --purge    # удалить всё, включая письма
```

Без ключа удаляются только контейнеры: письма, база, ключи и настройки
остаются, и `install.sh` поднимет сервер обратно в прежнем виде.

`--purge` удаляет тома с письмами и базой безвозвратно и требует ввести
слово `УДАЛИТЬ` — случайно так сделать нельзя. Docker, `/etc/letsencrypt`,
резервные копии и сам каталог проекта остаются.

## 10. Что установщик пока не делает

Честный список, чтобы не было сюрпризов:

- **Одно имя хоста у почты не настраивается.** Почта отвечает и на самом
  домене, и на `mail.<домен>`; выбрать что-то одно и заставить второе
  перенаправлять на первое установщик не умеет — это правка
  `infra/nginx/templates/app.conf.template`.
- **Админка снаружи не закрывается.** Если она нужна только из офиса или
  через VPN, ограничение прописывается руками (`allow`/`deny` в блоке
  `admin.<домен>` того же шаблона) или просто не публикуется DNS-запись
  `admin.<домен>` — тогда админка останется доступной лишь изнутри сервера.
- **Помощник на основе ИИ не подключается.** Ключ шифрования установщик
  генерирует, но какой сервис ИИ использовать и с каким ключом — это
  настройка в админке, а не вопрос при установке.
- **Брандмауэр не настраивается.** Если на сервере включён ufw, откройте порты
  сами: `ufw allow 25,80,110,143,443,465,587,993,995/tcp`.
- **Отправка через внешний релей не настраивается.** Если хостер наотрез
  отказывается открыть 25-й порт, письма придётся отправлять через чужой
  SMTP (`relayhost` в `infra/postfix/conf/main.cf.template` плюс
  `smtp_sasl_password_maps`) — это ручная правка.
- **Второй домен добавляется вручную** (через админку или SQL): установщик
  настраивает один основной домен.
