# Сборка руководства

Итог: `docs/Mail.True — руководство.pdf`.

## Как собрать

```bash
# 1. Показательный ящик со снимков (нужен поднятый стенд)
bash docs/manual/seed-demo.sh

# 2. Мастер первого запуска — только ради его снимков (см. ниже)
sudo bash install/web-install.sh
docker compose -f infra/docker-compose.yml logs installer   # ключ доступа

# 3. Снимки экрана
SHOT_INSTALLER_KEY='XXXX-XXXX-XXXX-XXXX-XXXX-XXXX' node docs/manual/shoot.mjs

# 4. Сам PDF
cd docs/manual && npm install     # один раз: marked
node docs/manual/build.mjs
```

Уборка после: `bash docs/manual/seed-demo.sh --clean` и
`docker compose -f infra/docker-compose.yml --profile installer down`.

## Как это устроено и почему

**Текст глав берётся из настоящих документов проекта** — `docs/install.md`,
`docs/autoconfig.md`, `docs/migration.md`. Не копируется, а читается при
сборке. Второй экземпляр тех же инструкций разошёлся бы с первым при первой
же правке, и человек, читающий PDF, получил бы шаги от прошлой версии
продукта.

Своё у руководства только то, чего в документах нет по существу, — файлы в
`src/`: титул и вводная глава, установка через браузер, обзор интерфейса со
снимками, глава про панель администратора, пошаговый перенос из Kerio Connect
и обслуживание.

**Порядок глав задан в `build.mjs`, а не номерами файлов.** Числа в именах
внутри `src/` — это порядок появления главы в проекте; главу, вставленную в
середину, дешевле добавить в список, чем переименовать четыре файла.

**Снимки делаются с отдельного показательного ящика**, а не с тестового.
Тестовый забит служебными письмами вида «outbound t178592812012296», и на
картинках в руководстве это выглядит так, будто продукт ими и занимается.
`seed-demo.sh` заводит ящик `demo@mail.local` с осмысленной перепиской,
тремя правилами фильтрации, двумя своими папками и подключённым внешним
ящиком — иначе страницы «Фильтры» и «Почта с других ящиков» снимались бы
пустыми, и руководство показывало бы возможности, которых будто нет.

**Браузером управляем напрямую по протоколу отладки**, без Playwright: в
Node 24 есть встроенный клиент WebSocket, а больше ничего и не нужно.
Полгигабайта зависимостей ради десятка снимков в сборку документации класть
незачем.

**PDF печатает обычный Chrome.** Шрифты и картинки вшиваются в разметку
целиком, поэтому документ собирается без сети и выглядит одинаково везде.

## Что нужно завести один раз

Учётная запись администратора для снимков панели — своя, чтобы пароль
администратора стенда не попадал в сборку документации:

```bash
HASH=$(printf '%s' 'manual12345' | docker compose -f infra/docker-compose.yml exec -T autoconfig node -e '
let pw = ""; process.stdin.on("data", (c) => { pw += c; });
process.stdin.on("end", () => {
  const { randomBytes, scryptSync } = require("node:crypto");
  const salt = randomBytes(16);
  const key = scryptSync(pw.normalize("NFKC"), salt, 32, { N: 16384, r: 8, p: 1, maxmem: 64*1024*1024 });
  process.stdout.write(["scrypt",16384,8,1,salt.toString("base64url"),key.toString("base64url")].join("$"));
});' | tr -d '\r\n')

docker compose -f infra/docker-compose.yml exec -T -e A_HASH="$HASH" postgres \
  sh -c 'psql -U mailserver -d mailserver -qtA -v hash="$A_HASH"' <<'SQL'
INSERT INTO admin_users (login, password_hash, display_name, role)
VALUES ('rukovodstvo', :'hash', 'Снимки для руководства', 'owner')
ON CONFLICT (login) DO UPDATE SET password_hash = EXCLUDED.password_hash;
SQL
```

Адреса и пароли переопределяются переменными окружения: `SHOT_EMAIL`,
`SHOT_PASSWORD`, `SHOT_ADMIN_LOGIN`, `SHOT_ADMIN_PASSWORD`, `WEB_URL`,
`ADMIN_HOST`, `STAND_ADDR`, `CHROME_PATH`, `INSTALLER_URL`,
`SHOT_INSTALLER_KEY`, `SHOT_NEW_DOMAIN`.

## Снимки, которые нельзя снять по адресу

Три экрана не открываются ссылкой, и их сценарии живут в `shoot.mjs` (поле
`act`). Ни один из них не доходит до подтверждающей кнопки: снимок нужен
именно с вопросом на экране.

**Мастер первого запуска** живёт отдельной службой под профилем `installer` и
на боевом сервере выключает себя после установки. Ключ доступа он печатает в
журнал контейнера и нигде не сохраняет, поэтому в файл его не положить —
только переменной `SHOT_INSTALLER_KEY`. Без неё три снимка мастера
пропускаются, а остальные делаются как обычно: это нормальное состояние
установленного сервера, а не поломка сборки. Шаг «Сертификат» — четвёртый, и
адресом он не достижим: мастер держит ответы в памяти вкладки, поэтому
сценарий проходит первые три шага так же, как прошёл бы человек.

**Диалог перезапуска службы** висит над «Настройками сервера». Открывается он
у сервера приложения намеренно: его перезапуск не требует посредника, поэтому
на стенде без `SERVICE_AGENT_TOKEN` диалог виден целиком, а не в виде отказа
«из панели сейчас нельзя».

**Смена домена** снимается с показательным планом: пустая страница показывает
одно поле ввода, тогда как объяснять надо ровно то, что появляется после
расчёта. План ничего не меняет на сервере (он считает и выпускает ключ DKIM), и
по окончании снимков отменяется — иначе стенд остался бы с чужим заданием, и
следующий запуск отказался бы составлять новый план.

## Грабли, на которые уже наступили

**Снимок формы входа делается ДО входа.** Вошедшего продукт уводит с формы
входа на «Входящие», и снимок формы получить уже нельзя.

**Панель администратора живёт на отдельном имени хоста** (`admin.<домен>`), а
не на отдельном порту. Локально имя подменяется флагом браузера
`--host-resolver-rules`, чтобы не править файл hosts машины, собирающей
документацию.

**Тело запроса с кириллицей нельзя передавать аргументом `-d` в curl.** В
оболочке Windows аргумент доезжает до curl уже в однобайтовой кодировке:
«договор» превращается в семь байт вместо четырнадцати, и сервер такое тело
не принимает. `seed-demo.sh` пишет тела в файл и передаёт через
`--data-binary @файл`. Из-за этого первые сборки молча заводили только
правила с латиницей, а на снимке было три одинаковых правила вместо трёх
разных.

**Колонка с адресом ящика в каждой таблице называется по-своему**
(`account_email`, `owner_email`, `email`). Первая версия уборки везде писала
`email`, запросы падали, вывод был заглушен — и уборка молча ничего не
делала. Правила накапливались от запуска к запуску. Теперь ошибки psql в
`seed-demo.sh` не подавляются.

**Сборщик внешней почты нельзя направлять на тестовый ящик.** В нём триста
служебных писем, и сборщик переливает их в показательный — то есть ровно тот
мусор, ради избавления от которого показательный ящик и заведён. Источник —
отдельный лёгкий ящик `staryi@mail.local` с одним письмом.

**Команды в руководстве надо запускать, а не переписывать.** Глава про перенос
из Kerio Connect в первой редакции содержала выдуманные команды: `mailbox`
вместо `run`, `--src-host` вместо `--source-host`, `--src-allow-insecure-tls`
вместо `--strict-tls` (да ещё с обратным смыслом), пароль аргументом вместо
файла. Взялись они оттуда, что глава писалась по памяти о документе, а не
сверялась с самой программой. Ни одна команда не сработала бы, а про пароли
руководство учило бы худшему из способов.

Теперь каждая команда главы прогнана на стенде: `kerio-users` на настоящей
выгрузке Kerio, `run --dry-run` на живом ящике (495 писем, 6 папок), состав
колонок CSV для `batch` — сверен с разбором в `packages/migrate/src/batch.ts`.
Правило простое: если команда попала в руководство, значит, её запускали.
