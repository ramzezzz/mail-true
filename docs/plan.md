# План работ

Живой документ: пополняется по мере исследования эталонного интерфейса.

## Что делаем

Почтовый сервер под Ubuntu Server 22 с веб-интерфейсом, повторяющим привычный почтовый интерфейс
вплоть до мелочей поведения — кроме рекламных блоков. Плюс админка, установщик
одной командой и перенос почты с других серверов.

## Главные требования

1. **Быстрый.** Список писем виртуализирован, ответ API — десятки миллисекунд,
   постоянные IMAP-соединения вместо переподключения на каждый запрос.
2. **Небольшой.** Минимум образов, alpine где возможно, скромное потребление
   памяти. Цель — рабочий сервер на VPS с 2 ГБ ОЗУ.
3. **Легко ставится.** Одна команда установки, интерактивный мастер первичной
   настройки, самопроверка после установки.

### Проверка требования «небольшой»

Замер на поднятом стеке в простое:

| Сервис    | Память     |
| --------- | ---------- |
| Rspamd    | 154 МБ     |
| Postgres  | 31 МБ      |
| Postfix   | 13 МБ      |
| Dovecot   | 12 МБ      |
| Redis     | 6 МБ       |
| **Итого** | **216 МБ** |

В цель укладываемся с большим запасом: на VPS с 2 ГБ остаётся более полутора
гигабайт на приложение, поисковый индекс и сами письма.

Отсюда же следует решение по проверке на вирусы: ClamAV с полными базами
занимает около гигабайта и съел бы половину запаса, поэтому он подключается
по желанию, а не по умолчанию, с честным предупреждением в установщике.

## Архитектура

```
              ┌─────────── браузер ───────────┐
              │  apps/web    — почта          │
              │  apps/admin  — админка        │
              └───────────────┬───────────────┘
                              │ REST + WebSocket
              ┌───────────────┴───────────────┐
              │   apps/api — Fastify + TS     │
              └──┬──────────┬─────────┬───────┘
           IMAP  │          │ SQL     │ submission
                 │          │         │
        ┌────────┴───┐ ┌────┴─────┐ ┌─┴────────┐
        │  Dovecot   │ │ Postgres │ │ Postfix  │
        │  Maildir   │ │  Redis   │ │  Rspamd  │
        └────────────┘ └──────────┘ └──────────┘
```

Почему Postfix и Dovecot, а не свой SMTP/IMAP на Node: доставляемость. Они
десятилетиями отлаживались против особенностей чужих серверов, а Rspamd даёт
DKIM, DMARC и фильтрацию спама из коробки. Свой велосипед означал бы, что письма
уходят в спам у получателей.

Postgres хранит аккаунты, домены, алиасы, настройки, фильтры и метаданные
интерфейса. Сами письма живут в Maildir и читаются через IMAP — единый источник
истины, никакой рассинхронизации между базой и почтовым хранилищем.

## Этапы

### 1. Каркас монорепозитория — готово

npm workspaces, TypeScript project references, общий пакет типов
`packages/shared` с доменной моделью почты.

### 2. Исследование интерфейса — готово

Снято с эталонного интерфейса: токены (1194 отобрано из 3341), 867 CSS-правил с
состояниями, геометрия всех основных узлов, поведение.

Результат — `docs/design-system.md` (метрики и стили) и `docs/features-reference.md`
(функциональность: настройки, фильтры, сборщик, поиск, цепочки, горячие
клавиши, контекстные меню). Сырые выгрузки и скриншоты — `справочник по вёрстке/`.

Три вывода повлияли на архитектуру:

1. Тело письма вставляется прямо в DOM без `iframe` — значит HTML санируется
   на сервере. Делаем так же.
2. Поиск находит слова внутри вложений и показывает фрагмент документа —
   нужен полнотекстовый индекс, штатного IMAP SEARCH мало.
3. Всё оформление держится на CSS-переменных — темы переопределяют только их.
   Поэтому в наших компонентах не должно быть ни одного зашитого цвета.

### 3. Почтовый стек в Docker — готово

Postfix + Dovecot + Rspamd + Postgres + Redis подняты, виртуальные домены и
ящики в Postgres, доставка через LMTP в Maildir, submission на 587 с SASL
через Dovecot, DKIM в Rspamd.

Проверено сквозным сценарием (`infra/test-delivery.sh`), 14 проверок из 14:
приём по SMTP, доставка в Maildir, чтение по IMAP с совпадением темы и тела,
отправка через submission с аутентификацией, наличие DKIM-подписи, отклонение
неверного пароля.

Порты на 127.0.0.1: 25, 587, 143, 993, 5432, **6380** (Redis — не 6379,
тот порт на машине разработки занят), 11334 (Rspamd).

### 4. API-бэкенд

Аутентификация с сессиями в Redis, мост к IMAP, отправка через submission,
WebSocket на IMAP IDLE для живого обновления списка.

### 5. Веб-интерфейс почты

1. Слой токенов и тем на CSS-переменных
2. Каркас: шапка, левое меню, колонки
3. Список писем с виртуализацией и всеми состояниями строки
4. Просмотр письма и цепочки
5. Окно написания
6. Поиск и фильтры
7. Настройки ящика

### 6. Полнотекстовый поиск

Штатный IMAP SEARCH не годится: он перебирает письма и ничего не знает про
содержимое вложений. А в привычных почтовых интерфейсах поиск находит слова внутри PDF и показывает
фрагмент документа — это надо повторить.

Берём **Dovecot FTS с Xapian**: встраивается прямо в IMAP SEARCH, не тянет Java,
занимает мало памяти. Solr отпадает по обоим требованиям — быстрый и небольшой.

Текст из вложений вытаскиваем при индексации отдельными разборщиками.
Агрегаты для фасетных фильтров (сколько совпадений в каждой папке, по месяцам
и годам) считаем из индекса, а не перебором.

### 7. Админка

Отдельное приложение со своей аутентификацией и ролями:

- **Пользователи**: создание, блокировка, смена пароля, квоты, алиасы,
  массовые операции, импорт из CSV
- **Домены**: добавление своего домена, проверка DNS (MX, SPF, DKIM, DMARC, PTR)
  с подсказками, что именно прописать у регистратора; генерация ключей DKIM
- **Вход в ящик пользователя от администратора** — без знания пароля,
  через служебный токен; каждый такой вход пишется в журнал аудита
- **Почтовый поток**: очередь Postfix, отложенные и отклонённые письма,
  журнал доставки с поиском по отправителю и получателю
- **Спам**: пороги Rspamd, белые и чёрные списки, обучение
- **Наблюдение**: занятое место, число писем, нагрузка, состояние сервисов,
  свободное место на диске, срок действия сертификатов
- **Резервные копии**: расписание, выгрузка и восстановление ящика
- **Журнал аудита**: кто из администраторов что менял и когда

### 8. Перенос почты с других серверов

Главный сценарий — **Kerio Connect**, но механизм универсальный: перенос идёт
по IMAP, поэтому работает с любым сервером, у которого есть IMAP (Kerio,
Exchange, Zimbra, обычный Dovecot, Яндекс, Gmail).

- Мастер переноса в админке: адрес исходного сервера, учётные данные,
  выбор ящиков, сопоставление папок
- Перенос сохраняет флаги, даты, структуру папок и, по возможности, UID
- Докачка: повторный запуск переносит только новое, ничего не дублируя
- Пакетный перенос многих ящиков по списку, с очередью и отчётом
- Отдельно: перенос учётных записей — выгрузка пользователей из Kerio
  и создание их у нас с временными паролями
- Прогресс и журнал по каждому ящику, возможность продолжить после обрыва

### 9. Несколько ящиков в одном интерфейсе

Переключение между своими ящиками без повторного входа — как в привычных почтовых интерфейсах, где
аватары аккаунтов лежат в шапке, а непрочитанные считаются по всем сразу.

Отдельно — подключение **чужих ящиков с других серверов** по IMAP. Два режима,
оба нужны, потому что решают разные задачи:

**Сборщик** (основной режим, так работает привычный почтовый интерфейс). Периодически забирает почту
с внешнего сервера и складывает в отдельную папку нашего ящика. Плюсы: письма
доступны офлайн, попадают в общий поиск, работают фильтры и цепочки. Минус:
занимают место дважды.

**Прямое подключение**. Внешний ящик показывается как отдельное дерево папок,
письма читаются с чужого сервера на лету, ничего не дублируется. Плюс: место не
занимается, всегда актуальное состояние. Минус: скорость зависит от чужого
сервера, общий поиск по нему не работает.

Что нужно в обоих режимах:

- Мастер добавления с автоопределением настроек по адресу (тот же механизм,
  что и для сторонних клиентов, только наоборот — мы ищем чужие настройки)
- Пароли внешних ящиков шифруются в базе, ключ отдельно от неё
- Отправка «от имени» внешнего адреса через его же SMTP
- Состояние сборщика: когда забирал в последний раз, сколько писем, ошибки

### 10. Сторонние почтовые клиенты и автонастройка

Ящик должен открываться в Thunderbird, Outlook, Apple Mail, мобильных клиентах —
причём пользователь вводит только адрес и пароль, а клиент сам находит настройки.

Протоколы наружу:

| Протокол        | Порт | Шифрование |
| --------------- | ---- | ---------- |
| IMAP            | 993  | TLS        |
| IMAP            | 143  | STARTTLS   |
| POP3            | 995  | TLS        |
| POP3            | 110  | STARTTLS   |
| SMTP submission | 465  | TLS        |
| SMTP submission | 587  | STARTTLS   |

Автоопределение делаем сразу тремя способами, потому что каждый клиент ищет
по-своему:

1. **Mozilla Autoconfig** — Thunderbird и совместимые.
   `https://autoconfig.<домен>/mail/config-v1.1.xml?emailaddress=…`
2. **Microsoft Autodiscover** — Outlook.
   `https://autodiscover.<домен>/autodiscover/autodiscover.xml`, отвечает на POST
   с XML-запросом. Плюс перенаправление с корневого домена.
3. **DNS SRV** — запасной путь для тех, кто не нашёл по HTTP:
   `_imaps._tcp`, `_submission._tcp`, `_pop3s._tcp`, `_autodiscover._tcp`.
4. **Профиль Apple** — выдача `.mobileconfig` для iPhone и macOS одной ссылкой.

Админка показывает готовые DNS-записи для всего этого и проверяет, что они
действительно опубликованы.

### 11. Помощник на основе ИИ

Подключается через API, поэтому не привязан к одному поставщику. В настройках
задаётся адрес, ключ и модель — подойдёт любой сервис с совместимым интерфейсом,
включая локальную модель на своём железе.

Что делает:

- **Краткое резюме** письма или всей цепочки — три-четыре строки вместо десяти
  экранов переписки
- **Умная группировка**: раскладывает входящие по смыслу, а не только по
  отправителю — счета, доставки, встречи, личное
- **Помощь с ответом**: несколько вариантов ответа с разным тоном, продолжение
  начатой фразы, исправление и сокращение текста
- **Извлечение полезного**: даты и встречи, суммы и счета, задачи и сроки,
  трек-номера — вытащить из письма и показать отдельно
- **Перевод** письма с сохранением вёрстки
- **Поиск обычными словами**: «письма от бухгалтерии про оплату в марте»
  превращается в запрос к почте

Настраиваемость обязательна на трёх уровнях: администратор разрешает или
запрещает ИИ по домену и ставит ограничение расходов, пользователь включает
отдельные возможности, каждая возможность работает только по явному действию
или, если включено, автоматически.

Про приватность отдельно: содержимое писем уходит стороннему сервису, и это
надо честно показать. Поэтому — выключено по умолчанию, явное согласие при
включении, список того, что именно отправляется, и возможность указать
локальную модель, чтобы письма вообще не покидали сервер.

### 12. Установщик и документация

- `install.sh` — одна команда: проверяет систему, ставит Docker при
  необходимости, спрашивает домен и пароль администратора, поднимает стек,
  выпускает сертификаты Let's Encrypt, показывает DNS-записи для настройки
- Мастер первичной настройки в админке
- Скрипт самопроверки: порты, DNS, сертификаты, доставка, обратная связь
- **Инструкция в PDF со скриншотами**: развёртывание с нуля, настройка
  домена и DNS, перенос почты с Kerio Connect, обслуживание и резервные копии

## Тестирование

Каждый этап заканчивается проверкой — без неё этап не считается закрытым.

| Слой          | Чем проверяем                                                                 |
| ------------- | ----------------------------------------------------------------------------- |
| Почтовый стек | Сквозная доставка: письмо через SMTP → Maildir → чтение по IMAP               |
| API           | Юнит-тесты на разбор писем и интеграционные на маршруты против живого Dovecot |
| Интерфейс     | Сборка без ошибок типов, компонентные тесты, прогон сценариев в браузере      |
| Админка       | Создание пользователя, вход под ним, проверка изоляции прав                   |
| Перенос       | Тестовый ящик-источник по IMAP, сверка числа писем, флагов и папок            |
| Установщик    | Установка с нуля в чистой Ubuntu 22.04 в контейнере                           |
| Целиком       | Сценарий «вход → список → чтение → ответ → отправка → проверка доставки»      |

### Заглушки лгут — проверять только против настоящего сервера

Первый же запуск интерфейса против живого API вскрыл три ошибки, которых не
видели ни типы, ни 50 тестов на заглушках:

1. Сервер отдаёт папки объектом-обёрткой `{ folders: [...] }`, а заглушка —
   голым списком. Интерфейс падал на первом же экране.
2. Интерфейс просил тысячу писем за раз, а сервер ограничивает страницу сотней.
   Список не грузился вообще.
3. У писем без отображаемого имени сервер отдавал пустую строку, а интерфейс
   подставлял запасное значение оператором `??`, который срабатывает только на
   `null`. Колонка отправителя была пустой.

Общая причина одна: заглушки писал тот же, кто писал интерфейс, поэтому они
согласованы с ожиданиями, а не с сервером. Отсюда правило: **заглушки годятся
для разработки вида, но ни один этап не закрывается, пока сценарий не пройден
против настоящего сервера**. И контракт между сторонами должен жить в
`packages/shared`, а не подразумеваться.

### Проверки нужно гонять подряд, а не поодиночке

Наборы проверок стека по отдельности были зелёными, а запущенные друг за
другом — падали через раз. Разбор занял время, но нашёл сразу несколько
настоящих дефектов, которые поодиночке не проявлялись:

1. **Глобальный фильтр Sieve не был скомпилирован заранее.** Dovecot пытался
   собрать его при каждой доставке письма, не мог (каталог принадлежит root)
   и писал по две строки ошибки на каждое письмо. Работало, но лишней работой
   на каждом письме. Компилируем при сборке образа.
2. **Проверка здоровья Dovecot не покрывала порт службы паролей.** Контейнер
   объявлялся здоровым, пока аутентификация ещё не слушала, — и Postfix,
   дождавшись «здоровья», ловил отказ на первой же отправке с паролем.
3. **У Dovecot не было постоянного адреса.** При пересоздании контейнера он
   получал новый, а долгоживущий процесс Postfix продолжал стучаться по
   старому. То есть обновление Dovecot ломало отправку до перезапуска Postfix.
4. **Сама плавающесть.** Причина оказалась не дефектом, а работающей защитой:
   `auth_failure_delay` задерживает ответ на неверный пароль, и следующие
   проверки встают в очередь. Измерено: после десяти неверных паролей первая
   верная проверка заняла 4536 мс вместо 400, вторая — снова 393 мс. Набор
   `test-delivery.sh` намеренно проверяет неверный пароль, следующий набор
   сразу отправлял письмо и упирался в таймаут. Настоящий почтовый клиент в
   такой ситуации повторяет отправку — так теперь делает и проверка.

Отдельно стоит записать, чего делать не надо: снять общий штраф через
`login_trusted_networks` для внутренней сети не помогло — измерение показало,
что на эту задержку оно не влияет. Послабление убрано: ослаблять защиту без
доказанной пользы незачем.

## Разделение работ между агентами

Браузер — единственный общий ресурс, поэтому исследование интерфейса веду сам,
а независимые части отдаю агентам в параллель. Каталоги у них не пересекаются:

| Агент                      | Каталог             | Состояние                            |
| -------------------------- | ------------------- | ------------------------------------ |
| Почтовый стек              | `infra/`            | в работе                             |
| API-бэкенд                 | `apps/api/`         | в работе                             |
| Токены и каркас интерфейса | `apps/web/`         | в работе                             |
| Админка                    | `apps/admin/`       | ждёт схему базы от стека             |
| Перенос почты              | `packages/migrate/` | ждёт готовый IMAP-стек               |
| Установщик и PDF           | `install/`, `docs/` | последним, когда есть что показывать |

## Открытые вопросы

Пока открытых нет.

Решённое:

- **Домен.** Реальный домен появится на этапе боевой установки. Поэтому вся
  разработка идёт на `mail.local`, а домен — параметр установщика, а не
  зашитое значение. Проверки SPF, DKIM, DMARC и PTR встраиваем в админку
  заранее, чтобы при установке сразу было видно, что настроено, а что нет.
- **Несколько ящиков.** Нужны, вместе с подключением чужих по IMAP — см. этап 9.
- **Акцентный цвет.** Берём свой `#006EC6` (True Blue), а не синий привычный почтовый интерфейс
  `#0077FF`. Причина не вкусовая: `#0077FF` на белом даёт контраст 4.13:1 и не
  проходит WCAG AA для текста, а `#006EC6` даёт 5.19:1. Тон при этом почти тот
  же, привычность интерфейса не теряется. Вся остальная геометрия и метрики —
  как снято с эталонного интерфейса.
- **Свой рекурсивный резолвер.** Добавляем в стек, потому что бесплатные списки
  Spamhaus отказываются отвечать на запросы через публичные резолверы вроде
  8.8.8.8. Без своего резолвера проверки молча не сработают — а это худший
  случай: фильтр вроде бы настроен, но не работает. Подробности —
  `docs/antispam-spec.md`.
- **Движок поиска.** Dovecot FTS с Xapian, не Solr: Solr тянет Java и сотни
  мегабайт памяти, что противоречит требованию «быстрый и небольшой».

## Чего не делаем

Календарь, облако, заметки, задачи и прочие сервисы портала привычный почтовый интерфейс в проект
не входят. Из шапки портала берём только внешний вид, без самих сервисов.
