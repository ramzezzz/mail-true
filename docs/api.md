# API Mail.True

Бэкенд: Fastify + TypeScript (`apps/api`). Работает поверх почтового стека
(Dovecot IMAP, Postfix submission, Redis); Postgres для API не обязателен.

## Запуск

```bash
cp apps/api/.env.example apps/api/.env   # поправить под окружение
npm run build --workspace @mail-true/api
npm run start --workspace @mail-true/api # node dist/server.js
```

Скрипты:

- `npm run test --workspace @mail-true/api` — сборка + юнит-тесты (node --test);
- `npm run smoke:imap --workspace @mail-true/api` — протокольная проверка стека
  (IMAP-вход, папки, отправка через submission, чтение из Входящих);
- `npm run smoke:api --workspace @mail-true/api` — сквозная проверка HTTP API
  (сервер должен быть запущен).

Конфигурация — переменные окружения (см. `.env.example`), валидируются zod-схемой
в `src/config.ts`. Важное в dev-стеке: `REDIS_URL` указывает на порт **6380**
с паролем из `infra/.env`; `TLS_REJECT_UNAUTHORIZED=false` из-за самоподписанных
сертификатов.

## Аутентификация

Вход проверяется реальным IMAP-логином к Dovecot. Сессия хранится в Redis
(`SESSION_STORE=memory` — отладочный режим без Redis), клиент получает
подписанную httpOnly-cookie `mt_session` (SameSite=Lax). Пароль пользователя
хранится в сессии зашифрованным (AES-256-GCM от `SESSION_SECRET`) — он нужен
для открытия IMAP/SMTP-соединений от имени пользователя. Каждый авторизованный
запрос скользяще продлевает сессию на `SESSION_TTL_SECONDS`.

| Метод | Путь                | Описание                                                                                                                                   |
| ----- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| POST  | `/api/auth/login`   | `{email, password}` -> `{ok, email}` + cookie. Лимит 10 попыток/мин с IP                                                                   |
| POST  | `/api/auth/logout`  | Удаляет сессию, закрывает IMAP-соединения пользователя. **Тела нет** — заголовок `Content-Type` на этот запрос ставить нельзя              |
| GET   | `/api/auth/session` | При действующей сессии — `{authenticated: true, email}` и продление сессии; без сессии — `401 UNAUTHORIZED`, а не `{authenticated: false}` |

## Форма ошибки

**Любая** ошибка API — включая ошибки самого Fastify и маршрутизатора —
приходит в одном виде:

```json
{ "error": "КОД", "message": "Текст по-русски", "details": … }
```

`details` появляется только там, где есть что уточнить (`VALIDATION` — список
полей, `SEND_REJECTED` — отклонённые получатели). Поле `error` — это КОД из
таблицы ниже, а не человеческий текст: интерфейс разбирает именно его.

| Код                      | Статус | Когда                                                                                  |
| ------------------------ | ------ | -------------------------------------------------------------------------------------- |
| `UNAUTHORIZED`           | 401    | Нет сессии или она истекла                                                             |
| `AUTH_FAILED`            | 401    | Неверные логин или пароль (именно отказ Dovecot по учётным данным)                     |
| `FORBIDDEN`              | 403    | Сессия есть, прав не хватает (админка)                                                 |
| `NOT_FOUND`              | 404    | Нет письма, папки или маршрута                                                         |
| `VALIDATION`             | 400    | Не прошла проверка схемы; `details` — список полей                                     |
| `BAD_REQUEST`            | 400    | Прочие некорректные запросы (в т. ч. битый адрес и слишком длинный параметр)           |
| `SEND_REJECTED`          | 400    | Почтовый сервер отказался принять письмо навсегда (например, `550`)                    |
| `UNSUPPORTED_MEDIA_TYPE` | 415    | Не тот `Content-Type`                                                                  |
| `PAYLOAD_TOO_LARGE`      | 413    | Тело запроса больше предела                                                            |
| `FILE_TOO_LARGE`         | 413    | Файл больше предела вложения                                                           |
| `MESSAGE_TOO_LARGE`      | 413    | Собранное письмо не пройдёт через почтовый сервер                                      |
| `RATE_LIMITED`           | 429    | Превышена частота запросов                                                             |
| `UPSTREAM_UNAVAILABLE`   | 503    | Почтовый стек недоступен: нет соединения, оно оборвалось, упёрлись в предел соединений |
| `INTERNAL`               | 500    | Внутренняя ошибка; подробности только в журнале                                        |

**Ошибки обратного прокси.** Когда сервер приложения недоступен целиком
(обновление, падение, ещё не поднялся), отвечает не он, а nginx. Такой ответ
тоже приходит в форме контракта — с кодом `UPSTREAM_UNAVAILABLE` и русским
текстом, но со своим HTTP-статусом: `502` (сервер приложения не отвечает),
`503` (временно недоступен), `504` (не ответил вовремя). Для интерфейса все
три означают одно: подождать и повторить. Подменяются ТОЛЬКО ответы,
сочинённые самим nginx: законный `503 UPSTREAM_UNAVAILABLE` от приложения
и `503` пробы состояния проходят как есть
(см. `infra/nginx/templates/app.conf.template`).

**Проба состояния.** `/healthz` краснеет (503), когда недоступна часть, без
которой продукт не работает: Postgres, Redis (при `SESSION_STORE=redis`),
IMAP. Отправка почты и антиспам в пробу намеренно не входят — без них
продукт работает хуже, но работает, а красная проба увела бы сервер
приложения из работы целиком и запустила бы круг бесполезных перезапусков.
Их состояние видно в `/health` и в сводке админки.

Отдельно про `AUTH_FAILED` и `UPSTREAM_UNAVAILABLE`. «Неверный пароль» —
только когда Dovecot прямо это сказал. Всё остальное, включая отказ по
пределу одновременных соединений (`Maximum number of connections from
user+IP exceeded`), — это 503. Иначе при упоре в предел вход становится
невозможен вовсе: на верный пароль приходит «Неверный адрес или пароль»,
пользователь начинает перебирать пароли и упирается ещё и в ограничение
попыток.

## Маршруты

Все — под сессией. Идентификатор письма — `folderId:uid` (например `inbox:42`);
идентификаторы папок: `inbox|sent|drafts|spam|trash|archive` либо
`f-<base64url(IMAP-путь)>` для пользовательских.

### Что важно знать про эти маршруты

**Список писем.** `filter=with-attachments` отбирает письма разбором
BODYSTRUCTURE — той же самой, по которой в списке рисуется скрепка, поэтому
фильтр и признак `hasAttachments` совпадают по определению. Поиском по
заголовку `Content-Type` это не делается: Dovecot по нему не ищет вовсе
(проверено — `doveadm search header content-type` не находит ничего, при том
что `header subject` работает). `snippets=0` отключает докачку сниппетов —
она стоит отдельного обращения к серверу на каждое письмо.

`search` — не просто слова: строка разбирается на операторы
(`от:`/`from:`, `кому:`, `копия:`, `тема:`, `есть:вложение`, `файл:`,
`после:`/`до:`, `новее:`/`старше:`, `больше:`/`меньше:`, слова-признаки
`непрочитанные`/`важные`), и они складываются с `filter` и `label`
логическим И. Всё, что не похоже на известный оператор, остаётся обычными
словами полнотекстового поиска — `Договор № 452/26: правки` ищется как
текст, а не как поле «452/26». Полная таблица и объяснения — в
`docs/search.md`, раздел «Язык поисковых запросов». Оператор `папка:`
разбирается, но условием поиска не становится: папку выбирает вызывающий
параметром `folderId`.

`label=mt-oplatit` отбирает письма по своей метке. Отбор делает Dovecot
командой `KEYWORD` по своему индексу, то есть по ВСЕЙ папке, и складывается
с `filter` и `search` логическим И. Служебное ключевое слово меткой быть не
может: `label=$Snoozed`, `label=finance`, `label=reliable` и любое слово без
приставки `mt-` отклоняются с 400 (`apps/api/src/mail/labels.ts`). С
`threaded=true` отбор уживается сам собой: строка-разговор собирается из
писем, прошедших поиск, поэтому разговор попадает в список, если метка стоит
хоть на одном его письме. Замер на живом ящике (483 письма, помечено 100):
первая страница с отбором — 34 мс против 41 мс без него; весь отобранный
список — 96 мс одним запросом против 434 мс и пяти запросов, которыми
приходилось вычитывать папку целиком, пока отбор считался в браузере.

Номера писем уходят в IMAP **свёрнутыми в диапазоны и разбитыми по
командам** (`1:20000`, не длиннее 8 КБ на команду). Это не оптимизация,
а условие работоспособности: строка команды IMAP ограничена, и весь
список номеров одной строкой Dovecot отвергает — `Too long argument`.
Проверено на живом ящике из 20 000 писем: перечисление всех номеров даёт
команду в 119 999 символов и `BAD ... Too long argument`, свёрнутый
диапазон отдаёт все 20 000 структур. Фильтр «с вложениями» на таком ящике
отвечает за ~0,7 с.

**Отказ поиска — это ошибка, а не пустой результат.** imapflow при неудаче
SEARCH исключения не бросает, а возвращает `false`. Если это принять за
пустой список, повреждённый индекс превращается в честное на вид
`{"items":[],"total":0}` с кодом 200 — и человек уверен, что писем нет.
Любой неответ поиска — `503 UPSTREAM_UNAVAILABLE`.

**Вложения.** Вложенное письмо (`message/rfc822`, «переслано как вложение»,
исходник в отбойнике) — это вложение: у него нет ни `Content-Disposition`,
ни имени файла, поэтому имя берётся из темы вложенного письма и получает
расширение `.eml`. Части ВНУТРИ такого вложения отдельными вложениями
не показываются.

`size` вложения — размер **файла**, а не части письма. В BODYSTRUCTURE
лежит размер уже в base64, то есть примерно на 37% больше: файл на
3 000 000 байт приезжает как 4 105 262. Пересчёт обратный и точный
(4 символа на 3 байта плюс CRLF каждые 76 символов), проверен живьём —
показанный размер совпадает с числом скачанных байт. Для
`quoted-printable` пересчёта нет: там раздувание зависит от содержимого.

**Флаги и перемещение** сначала проверяют все папки списка и только потом
меняют хоть что-то: если хоть одной папки нет, приходит 404 и ящик остаётся
нетронутым. Счётчики `updated` и `moved` считаются по ящику, а не по длине
присланного списка: операция над несуществующим письмом даёт `0`.

**Отправка.** Postfix отвечает по каждому получателю отдельно, поэтому
`rejected` — обычное дело: письмо ушло не всем. `ok` равно `false`, как
только отклонён хотя бы один адрес; в `rejected` лежат адрес, код ответа
SMTP и его текст. Если письмо отвергнуто целиком и навсегда (`550`, `552`),
приходит `400 SEND_REJECTED` или `413 MESSAGE_TOO_LARGE` — не 503, потому
что сервер доступен и повтор не поможет. Текст письма при этом **не
теряется**: он сохраняется в черновиках, идентификатор — в `details`.

Текст письма не теряется и при **временном** отказе (сервер недоступен,
перезапуск служб, обновление продукта): `503 UPSTREAM_UNAVAILABLE` тоже
приходит с `details: {draftId, draftUid}`, а черновик лежит в «Черновиках».
Загруженные вложения при временном отказе намеренно **не удаляются**:
повторная отправка из того же окна ссылается на те же идентификаторы
загрузок. Их убирает уборщик загрузок.

Всё, что случилось **после** успешной передачи письма, отправку не
отменяет. Копия в «Отправленные» может не лечь (например, ящик
переполнен) — тогда ответ по-прежнему `200`, `ok: true`,
`sentMessageId: null`, но `savedToSent: false` и заполнено `warning`.
Раньше на этом месте приходила `500 INTERNAL`: письмо получатель уже
получил, копии не было, человек отправлял второй раз — и у получателя
оказывались два одинаковых письма. Флаг «отвечено» на исходном письме
(по `inReplyTo`) ставится там же и по тем же правилам: не получилось —
пишем в журнал, ответ не меняем.

**Черновики.** Автосохранение должно присылать `draftKey` — постоянный на
всё время жизни окна написания идентификатор. Пока у черновика ещё нет UID,
только по нему сервер и может понять, что несколько одновременных
сохранений относятся к одному письму. Сохранения одного окна выполняются
строго по очереди, а устаревший `draftUid` от клиента разрешается в
актуальную версию — поэтому копии черновика не плодятся.

**Отписка.** `POST /api/messages/:id/unsubscribe` разбирает `List-Unsubscribe`
и `List-Unsubscribe-Post`:

- отправитель разрешил отписку в один запрос (RFC 8058) и дал `https`-ссылку
  -> сервер сам шлёт `POST … List-Unsubscribe=One-Click` -> `{ok: true,
method: "one-click"}`. Запрос идёт с сервера намеренно: служба отписки не
  должна узнавать ни адрес читающего, ни его cookie;
- есть только `mailto:` -> сервер отправляет письмо отписки от имени
  пользователя -> `{ok: true, method: "mailto", address}`;
- есть только обычная ссылка -> `{ok: false, method: "link", url}`, страницу
  открывает интерфейс;
- в письме нет ни того, ни другого -> `404 NOT_FOUND`.

Адрес из письма проверяется дважды — по виду (только `https`, без учётных
данных и нестандартных портов) и по тому, куда разрешается имя: во
внутреннюю сеть сервер не ходит. Перенаправления не выполняются.

Ровно тот же код выполняет отписку ПАЧКОЙ (`POST /api/mailings/unsubscribe`)
— он вынесен в `mail/unsubscribe-request.ts`. Копии там быть не должно: в
этом коде живут проверки от SSRF, и разойдись две копии, вторая точка входа
однажды осталась бы без них. Разница только в исходе «отписаться нечем»: у
одного письма это `404`, у группы — `404` с именем группы в тексте.

**Разбор ящика (`/api/mailings`, `/api/cleanup`).** Оба маршрута отвечают по
одному и тому же СНИМКУ ящика: сервер читает заголовки, флаги и размеры
писем всех папок, кроме черновиков, и держит результат пять минут. Осмотр
ограничен сверху (5000 писем, свежие первыми) и честно об этом сообщает
(`truncated`, `scanned`, `total`): числа разбора — это то, на что человек
нажимает «удалить», и выдавать часть ящика за весь нельзя. Базы у разбора
нет и миграции тоже: он целиком считается по содержимому ящика.

**Массовая уборка (`POST /api/cleanup/sweep`).** Один маршрут на все виды
уборки — «всё от этого отправителя», «всё старше года», «оставить только
последнее», «переложить в папку»: это одно действие с разными условиями, и
трёх мест, где можно ошибиться в отборе, быть не должно. Защита:

- `dryRun: true` (по умолчанию!) только считает. Предпросмотр и выполнение
  зовут ОДНУ функцию отбора, поэтому показанное число и уехавшие письма не
  могут разойтись;
- выполнение требует `scanAt` — отметку снимка, который человек видел. Снимок
  с тех пор пересобран — `400`, а не «уберём по новым данным»;
- письма ПЕРЕНОСЯТСЯ (в корзину либо в названную папку). `EXPUNGE` этот
  маршрут не вызывает никогда;
- корзина, черновики и «Отложенные» не убираются ни при каких условиях;
- `moved` считается по ящику (UIDPLUS), а не по длине отбора: письмо, которое
  успели убрать с телефона, в «перенесено» не попадает.
  | WS | `/ws` | Уведомления: `{type: 'ready'}` при подключении, `{type: 'new-message', folderId, id, uid, from, subject, date}` по IMAP IDLE |

## Помощник на основе ИИ

`src/ai/`. Подключает пакет `@mail-true/ai`; требования к приватности —
`docs/ai-spec.md`, схема — миграция `0004_ai.sql`.

Настройки на трёх уровнях: **администратор** домена (`ai_domain_settings`:
разрешён ли ИИ, адрес сервиса, модель, ключ доступа, предел расходов),
**пользователь** (`ai_user_settings`: согласие и набор возможностей),
**действие** (проверка на каждом вызове). Нижний уровень не может разрешить
то, что запретил верхний.

Ключ доступа хранится зашифрованным (AES-256-GCM); ключ шифрования — только
в переменной окружения `AI_ENCRYPTION_KEY`, в базу не попадает. Наружу ключ
не отдаётся никогда, даже администратору: в ответе лишь подсказка `…a3f9`.

Пока администратор не включил помощника, `/api/ai/state` отвечает
`{enabled: false}` с пустыми полями — интерфейсу нечем нарисовать кнопки.
Это осознанно: пользователь не должен видеть кнопку, которая откажет.

| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------- |

`disclosure` — опись того, что реально ушло наружу: поля с их значениями,
что вырезано (подписи, цитаты, заголовки), какие вложения исключены.
Если `cached: true`, то `disclosure: null` — наружу не уходило ничего.

Админские маршруты (`/api/admin/ai/*`, права `domains.read`/`domains.write`/
`audit.read`): справочник возможностей, настройки по домену, живая проверка
связи и журнал обращений.

Коды отказов: `AI_DISABLED` (403, администратор выключил), `AI_CONSENT_REQUIRED`
(403, нужно согласие или сервис сменился), `AI_FEATURE_OFF` (403),
`AI_UNAVAILABLE` (503, нет настроек или базы), `AI_BUDGET_EXCEEDED` (429),
`AI_UPSTREAM` (502, сервис ИИ не ответил). Ни один из них не мешает читать
и отправлять почту.

Правила транслируются в **Sieve** и кладутся в личный файл пользователя
`/var/mail/vhosts/<домен>/<ящик>/.dovecot.sieve` (плюс исходник в
`sieve/mailtrue.sieve`), после чего компилируются `sievec`. База —
источник истины: при любом изменении файл переписывается целиком.

**Регистр в условиях с кириллицей.** Способ сравнения Sieve по умолчанию
(`i;ascii-casemap`) сворачивает регистр только для латиницы: правило
«REPORT» ловит «Monthly report», а правило «ОТЧЁТ» письмо «Квартальный
отчёт за август» НЕ ловило. Поэтому условие, в значении которого есть
буквы вне ASCII, переводится в `:regex` с перечислением регистров каждой
буквы — `header :regex "subject" "(О|о)(Т|т)(Ч|ч)(Ё|ё)(Т|т)"` — и в
`require` добавляется `regex`. Латиница остаётся на `:contains`/`:is`/
`:matches`: с ней компаратор справляется сам.

Что не подошло (проверено на Dovecot 2.3.19 / Pigeonhole 0.5.19):
`:comparator "i;unicode-casemap"` Pigeonhole не знает вовсе; расширение
`variables` с `set :lower` кириллицу не приводит к нижнему регистру;
скобочные классы `[Оо]` в `:regex` разбираются побайтово и не работают.
Регистр — единственное, что становится безразличным: «отчет» и «отчёт»
по-прежнему разные слова.

Условия: «От», «Кому», «Тема», «Копия», «Переадресовано от/для», «Размер».
Действия: в папку, пометить прочитанным, пометить флажком, переслать копию
(`redirect :copy`), отвечать автоматически (`vacation`), применять к спаму,
продолжать другие фильтры. Правила без флага «применять к спаму» получают
явную защиту `not header :is "X-Spam" "Yes"`.

Как API добирается до хранилища, задаёт `SIEVE_TRANSPORT`:
`local` (каталог виден процессу API), `docker` (через контейнер Dovecot),
`off` (правила остаются только в базе — и это видно в ответе).

Два режима подключения чужого ящика (docs/plan.md, этап 9):

- **Сборщик** — периодически забирает почту к нам в папку. Перенос делает
  `@mail-true/migrate` (тот же код, что и миграция с чужих серверов):
  дедупликация по Message-ID и по содержимому папки-приёмника, докачка
  по курсору UIDVALIDITY/UID, сохранение флагов и внутренней даты.
  Повторный запуск не создаёт дублей даже после потери журнала докачки.
- **Прямое подключение** — отдельное дерево папок, письма читаются на лету.

(AES-256-GCM, `EXTERNAL_ACCOUNTS_KEY`, ключ рядом с базой не лежит).

не сохраняется ни при каких условиях.

Сбор по расписанию выполняется планировщиком внутри API и входит в ящик
владельца служебным пользователем Dovecot (`ящик*mtadmin`), потому что
в момент сбора сессии владельца может не быть. Без служебного доступа
сбор доступен только вручную из активной сессии.

## Подсказка адреса

| Метод | Путь                                | Описание                                                                              |
| ----- | ----------------------------------- | ------------------------------------------------------------------------------------- |
| GET   | `/api/contacts/suggest?q=&exclude=` | Подсказка по началу слова: до восьми адресов, `exclude` — уже введённые через запятую |
| POST  | `/api/contacts/hide`                | `{address}` — убрать адрес из подсказок навсегда                                      |
| POST  | `/api/contacts/restore`             | `{address}` — вернуть убранный адрес                                                  |

Ответ подсказки: `{items: [{address, name, own}], complete}`. `own` — человек
писал по этому адресу сам; `complete` — указатель переписки разобран целиком
(пока `false`, «ничего не найдено» означает «ещё не всё просмотрено»).

Источник подсказок — сама переписка: отправители полученных писем и
получатели отправленных. Указатель лежит в Postgres (`mail_contacts`,
миграция 0017) и наполняется сборщиком, который читает конверты порциями
от свежих писем к старым (`src/contacts/harvester.ts`) — спрашивать IMAP на
каждую букву нельзя, это секунды ожидания. Пополнение из ВХОДЯЩИХ писем
управляется переключателем «Автоматически пополнять контакты» в общих
настройках ящика; отправленные собираются всегда.

Указатель привязан к ящику: адрес владельца берётся из сессии, указать
чужой негде. При удалении ящика строки убираются вместе с настройками и
подписями (`AdminDb.purgeMailboxData`).

Подсказка не даёт отказов: при недоступной базе, неприменённой миграции
или ошибке запроса маршрут отвечает `200` и пустым списком. Подсказка —
помощь, а не действие; сообщение об ошибке в момент набора адреса мешало
бы сильнее, чем её отсутствие.

## Санитизация HTML писем

`src/mail/sanitize.ts` (DOMPurify + jsdom):

- вырезаются `script`, `iframe`, `object/embed`, формы, `on*`-обработчики,
  `javascript:`-ссылки, `@import`/`expression()` в CSS;
- `cid:`-картинки переписываются на `/api/messages/:id/parts/:partId`;
- внешние `http(s)`-картинки по умолчанию блокируются: `src` заменяется
  прозрачным пикселем, оригинал сохраняется в `data-mt-src`, число блокировок
  возвращается в `blockedRemote` — фронтенд показывает плашку
  «Показать картинки» и либо перезапрашивает письмо с `?images=1`, либо
  переносит `data-mt-src` в `src` на клиенте;
- ссылки получают `target="_blank" rel="noopener noreferrer"`;
- HTML-вложения отдаются как `text/plain` + `X-Content-Type-Options: nosniff`.

## Заголовки письма в ответе

`Message.headers` — отобранные заголовки, **имена всегда в нижнем регистре**:
`return-path`, `list-id`, `list-unsubscribe`, `list-unsubscribe-post`,
`list-help`, `list-post`, `list-owner`, `list-archive`, `x-mailer`,
`user-agent`, `authentication-results`, `content-language`, `importance`,
`x-priority`, `precedence`, `auto-submitted`.

Значения берутся из исходных строк заголовков (`headerLines` mailparser),
а не из его разобранного представления. Это принципиально: mailparser
сводит всю группу `list-*` в один объект под ключом `list`, а `return-path`
разбирает в адресный объект — при чтении «по имени» и то и другое терялось,
и письмо рассылки приходило с `headers: {}`. Кнопка «Отписаться» при этом
была недостижима в принципе.

## Пределы размеров

Три предела связаны друг с другом, и связь эта неочевидна:

| Настройка                  | Значение    | Смысл                                                                                   |
| -------------------------- | ----------- | --------------------------------------------------------------------------------------- |
| `MESSAGE_MAX_BYTES`        | 26214400    | Предел письма на почтовом сервере. Обязан совпадать с `message_size_limit` Postfix      |
| `UPLOAD_MAX_BYTES`         | 26214400    | Заявленный предел загрузки                                                              |
| `UPLOAD_MAILBOX_MAX_BYTES` | 262144000   | Сколько места один ящик может занять незавершёнными вложениями                          |
| `ATTACHMENT_MAX_BYTES`     | вычисляется | Действующий предел вложения: `min(UPLOAD_MAX_BYTES, MESSAGE_MAX_BYTES / 1.4)` ≈ 17,9 МБ |
| `COMPOSE_BODY_MAX_BYTES`   | 12582912    | Предел тела запроса на `/api/messages/send` и `/api/drafts`                             |

Почему предел вложения ниже предела письма: в письме вложение едет в base64,
а это +33% плюс переносы строк — итого около 1,37 раза, и ещё заголовки
частей. Если разрешить загружать ровно столько, сколько принимает Postfix,
файл больше ~19 МБ не уйдёт НИКОГДА, хотя загрузка примется. Именно так и
было; теперь предел выводится из предела письма, а при старте в журнал
пишется предупреждение, если заявленное значение пришлось уменьшить.

Предел тела запроса на маршрутах написания отдельный и больше общего (2 МБ):
`bodyHtml` по схеме допускает до 10 МБ, и письмо со вставленными картинками
законно бывает таким. Раньше оно упиралось в общий предел и получало
английскую ошибку не из контракта.

## Архитектура

- `src/imap/pool.ts` — пул IMAP-соединений: **ровно одно** на пользователя,
  закрытие после `IMAP_POOL_IDLE_MS` простоя. Соединение берётся уже внутри
  очереди задач пользователя, поэтому параллельные запросы не могут открыть
  второе: 60 одновременных запросов дают одно соединение (проверено
  `doveadm who`). Если соединение оборвалось посреди работы, задача получает
  `503 UPSTREAM_UNAVAILABLE`, сломанное соединение забывается, и следующая
  задача очереди открывает новое. Повтора оборванной операции нет намеренно:
  она может быть неидемпотентной (APPEND, перемещение);
- `src/ws.ts` — отдельное IDLE-соединение на пользователя для WebSocket,
  закрывается с уходом последнего сокета;
- `src/imap/service.ts` — папки/список писем/поиск (IMAP SEARCH + FETCH,
  сниппеты докачиваются из текстовой части с `maxBytes`);
- `src/mail/*` — чистые функции (маппинг папок, BODYSTRUCTURE, сниппеты,
  MessageSummary, разбор письма) — покрыты юнит-тестами `*.test.ts`;
- rate limit: 300 запросов/мин с IP глобально, 10/мин на login.

## Известные ограничения

Настройки, фильтры и подключение ящиков:

- **Два автоответа на одно письмо обрывают всю цепочку правил.** Sieve
  допускает автоответ один раз за исполнение. Правило с «отвечать
  автоматически» вместе с включённым общим автоответчиком (или два таких
  правила) роняют скрипт целиком: не срабатывает ни одно правило ниже,
  автоответ не уходит, письмо остаётся во «Входящих». Интерфейс обе
  настройки предлагает и обе сохраняет успешно, ни о чём не предупреждая.
- **Поиск не находит письмо по теме, присланной в восьмибитной кодировке
  без RFC 2047.** Сама тема теперь показывается правильно — она
  восстанавливается по кодировке тела (`mail/header-charset.ts`), — но ищет
  Dovecot по своему индексу, где лежат исходные байты в KOI8-R или CP1251.
  Поиск по телу такого письма работает: у тела кодировка объявлена честно.
- **Сбор по POP3 не реализован**: `protocol: 'pop3'` отклоняется с понятной
  ошибкой, а не сохраняется молча. Работает только IMAP.
- **`leaveOnServer`** сохраняется, но ни на что не влияет: письма на
  источнике не удаляются никогда.
- **`applyFilters`** сохраняется, но не работает: собранные письма кладутся
  IMAP-командой APPEND, а Sieve исполняется только при доставке.
- Пересылка копии и автоответ не применяются к уже полученным письмам —
  разослать письма задним числом нельзя отменить.
- Поля «Переадресовано от/для» поддержаны сервером, но в контракте
  веб-интерфейса их нет: правило с таким условием, сохранённое из формы,
  потеряет это условие.

- `threaded=true` группирует письма в переписки: строка списка — одна на
  разговор, при ней приходит сводка `thread` (все идентификаторы писем,
  число писем, непрочитанные, флажок, вложение, свои метки, участники), а
  `total`
  считает переписки, а не письма. Цепочки собирает сам Dovecot командой
  `UID THREAD REFS UTF-8 ALL` — по References и In-Reply-To, без склейки
  по одинаковой теме. В папках `drafts`, `trash`, `spam` и `snoozed`
  признак не действует: там приходят за одним конкретным письмом
  (`apps/api/src/mail/threads.ts`). Замеры на живом ящике: 483 письма —
  11 мс против 14 мс, 20 000 писем — 34 мс против 90 мс (без сниппетов);
- фильтр `with-attachments` перебирает BODYSTRUCTURE всех писем папки. Данные
  берутся из кэша индекса Dovecot, но на очень больших папках это заметно
  дороже обычного списка: замер на 20 000 писем — около 0,7 с против 0,4 с
  у обычного списка;
- размер вложения с кодировкой `quoted-printable` показывается как есть
  (закодированным): однозначного обратного пересчёта для неё нет. Файлы
  такой кодировкой практически не ездят — это кодировка текстовых частей;
- отправка не дожидается доставки: `rejected` показывает только то, что
  отверг наш Postfix при приёме. Отказ, случившийся дальше, приходит
  отбойником отдельным письмом;
- отложенная отправка (`sendAt`) не реализована — вернётся 400;
- квота отображается, только если в Dovecot включён плагин quota (иначе 0);
- подпись/аватар в `Account` пока статичны (нет хранилища профилей).
